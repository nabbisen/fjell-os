## What this release is

**One scheduler bug, and the three assumptions it had been silently holding
up.**

No new capability. 0.25 made the project interactive; 0.26 fixes a defect in
how tasks are scheduled and then deals with what that defect had been propping
up — which turned out to include a shipped feature, a kernel contract, and a
test that has been passing for the wrong reason.

Each of the three was invisible for the same reason: **a scheduler bug happened
to make it true.**

## What shipped

### RFC-0.26-001 — the scheduler priority defect

`PRIORITY_USER` existed **three times with two values**: `scheduler.rs`'s real
`32`, a *local* `const` shadowing it at `2` in `spawn.rs`, and a third hardcoded
`2` in `sys_task_start`. `priority_to_bucket` puts those in different buckets and
`dequeue_next` always drains the higher first, so **`init` preempted every other
spawned task**.

**The investigation was the deliverable, not the fix.** Correcting the constant
alone hung M6 boot, and the cause is `svc-timeout` — RFC 042's negative-test
service, an infinite `sys_yield()` loop *by design*, spawned in the M4 era. Its
first enqueue went through `sys_task_start`'s literal; every enqueue after its
first yield through `spawn.rs`'s constant. Fix one and not the other and it
occupies bucket 1 permanently, and bucket 0 is never reached again.

Recorded at `docs/rfcs/RFC-0.26-001-scheduler-priority-unification-investigation.md`.

### RFC-0.26-004 — readiness gets a single receiver

Removing the priority asymmetry stopped the ABDD live path running **at all**.
The first attempt to fix that could not be built, **and the escalation is what
found the real defect**: `semantic-stream` and `proxy-text` each announced
readiness *into their own endpoint*, while `init` held **receive-capable**
capabilities to those same objects. Two receivers on one queue, nothing
arbitrating, and readiness sharing a channel with protocol traffic.

**Invariant established: a service's endpoint has exactly one receiver.**
`init`'s capability to object 7 is narrowed to `CALL` and its capability to
object 8 removed, so a future `sys_ipc_recv` fails at the kernel boundary rather
than silently reintroducing the hazard.

`wait_ready_exact` is **deleted**, not patched — it discarded non-matching
messages without replying, leaving callers blocked forever. Observed live
swallowing `semantic_stream::PUBLISH_BEGIN`.

### RFC-0.26-002 — superseded, and worth recording

Its premise was false: it asserted a usable readiness signal already existed.
The implementer checked instead of believing it, found it did not, and **stopped
rather than approximating** — as its own D1 required, with approximations
available that would have gone green. It is in `archive/`, the first use of that
folder since it was created empty.

### E-022 is the one to read

`sys_ipc_send`'s `Queued` arm calls `block()` on the **sender**, while
`sys_ipc_try_send` is named `try_send` and documented as queuing and returning.
It self-deadlocks any task announcing a one-way message into an endpoint only it
receives on.

**Previously masked by the very arrangement E-021 removed** — `init` was already
waiting as an unsynchronised co-receiver, so the send always found a receiver
and never queued. Removing that co-receiver, correctly, removed the cover.

Worked around by deleting the two call sites, which were dead under the new
invariant anyway. **The kernel defect remains** for any future one-way send.

## Accepted risk

**A test is green for a reason nobody guarantees.** `test-all` is 21/21, and
the `ipc` profile passes again as a side effect of the ABDD fix —
`sample-service` now reaches its main loop and serves the message
`fjell-neg-test` depends on.

**E-019 was not closed**, and the profile passing is the reason to be careful
rather than the reason to close it. The assumption at `fjell-neg-test:435-439`
is still written, still unsynchronised, and now satisfied by accident. A red
test that is red for a known reason is honest; **a green test that is green for
a reason nobody guarantees is what this project has spent five milestones
removing.** RFC-0.26-003 is re-framed accordingly and remains open.

Also carried:

- **The invariant is enforced against `init` and behaviourally true elsewhere.**
  `ALL_NON_META` includes RECV, so `sample-service` and `proxy-text` still hold
  receive-capable capabilities to object 7, and `semantic-stream` to object 8.
  None receives there; none is prevented from doing so. A follow-up, not a
  reopen.
- **The 0.24 audit's findings are unchanged**, and its 22 `sound` verdicts
  remain provisional under E-017.

## What this release does not claim

No new capability, no new syscall, no ABI change. What changed is that three
things which appeared to work, and one which had stopped, now do so **for
reasons that are written down** rather than because a scheduler bug happened to
arrange it.
