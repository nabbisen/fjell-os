## What this release is

The first milestone in this project whose subject is **the verification
apparatus itself** rather than the system it verifies.

No new OS functionality. No kernel, ABI, capability, lease, IPC, or crypto
behaviour change. What changed is how much of this project's own evidence can
be believed.

Eleven instances of an instrument reporting success without having checked had
been found before this line. **Every one was found incidentally**, while doing
something else. Eleven for eleven, by accident — a discovery process that is
luck with good record-keeping.

- **RFC-0.24-001 — the instrument audit.** One question asked of every gate,
  tier, CI job, and committed artifact: *what would make this report success
  without having checked?* Four passes, a five-mode taxonomy, and one rule —
  an instrument with no demonstration is `UNAUDITED`, never `sound`.
- **RFC-0.24-002 — the seven repairs that could not wait**, including a first
  mechanical gate that passed on a workspace that did not compile and a CI job
  named "Property tests" that ran zero.
- **RFC-0.24-003 — ABI snapshot identity.** Found by re-deriving a `sound`
  verdict rather than by any failure: the gate guarding the ABI could not
  identify 45 of its own 423 items, and had never seen two functions in the
  crate that carries the syscall ABI.

**Result: 58 instruments — 22 sound, 33 findings, 3 `UNAUDITED`.** Before this
line, all of them were reporting green.

### Criteria 4/5 — the repro tier failed first, and why

The first full `test-all` run of this cut returned **18/19**, with tier 5
(reproducible build) red:

```
DIGEST DIFFERS: crates/fjell-kernel/prebuilt/fjell-neg-test.bin
  baseline = 988b72ff…
  current  = bc99f93a…
```

Recorded here rather than quietly fixed, because "regenerate the baseline until
it goes green" is precisely the move this milestone spent three RFCs forbidding.

**Diagnosis, before any regeneration.** Reverting `[workspace.package] version`
to `0.23.0` and rebuilding reproduced the committed baseline digest **exactly**;
restoring `0.24.0` and rebuilding twice produced `bc99f93a` **both times**. The
build is deterministic; the **workspace version is one of its inputs**, through
Cargo's `-C metadata`. No source line changed.

**Regeneration, verified.** The baseline was deleted and re-recorded — the tool
refuses to overwrite one in place by design (RFC-v0.21.3-001 §M4) — and the
result checked:

```
$ git diff --numstat tests/repro/baseline-digests.txt
1       1       tests/repro/baseline-digests.txt
```

**Exactly one line, for the one binary the evidence explains.** Had more moved,
the regeneration would have been absorbing something unexplained.

**The underlying gap was in the procedure, not the tree.** The exit criteria
never said to re-record the baseline after a version bump. The `0.23.0` cut hit
the same thing and handled it correctly, but the knowledge was never written
down, so it was rediscovered as a red tier. **Now written into
`docs/src/release/v0-release-cycle.md`** as a step before criterion 4, with the
verification requirement attached. No erratum: the gap is closed in the same
release that found it.

### The ABI gate

Four defects plus one found by the repair's own new check:

- **45 of 423 items never compared** — the key omitted `module` and collected
  into a `BTreeMap`, so duplicates silently overwrote.
- **15 items named `fn`** — `pub const fn` misparsed.
- **2 items absent entirely** — `pub unsafe fn` matched no pattern, so
  `sys_audit_drain_ptr` and `sys_audit_drain_raw` had never appeared in any
  snapshot.
- **162 items mis-attributed** — inline `mod` blocks untracked.
- **17 phantom items** — a file with no `mod` declaration anywhere, scanned as
  public ABI.
- **Methods lacked impl scope** — found by the new duplicate-key check on its
  first run.

The baseline was regenerated under a corrected scanner. That is the most
dangerous action in the line, because a genuine breaking change would have been
absorbed and lost. It was guarded by a reconciliation **registered in advance**
(B 15, B′ +2, C 162, D −17, E ~60, unexplained 0) and reproduced independently
by the reviewer: every difference assigned a cause, zero unexplained, net
`423 − 17 + 2 = 408` exactly.

## Accepted risk

**This milestone made the instruments more honest, not honest.**

Thirty-three findings remain open. Their instruments are still green. Each is
recorded in the register, grouped by root cause, disclosed as an erratum, and
scheduled as a 0.25 candidate — but none is fixed, and this release is cut with
them outstanding.

The sharpest of them is **E-017**, and it applies to this record. The audit's
own standard is that a `sound` verdict requires a committed demonstration of
the instrument failing. Two rows were found violating it, on opposite sides of
the review boundary. Gate 4 was the first of the remaining rows re-derived and
it fell immediately, so the base rate is not known to be low.

**The 22 `sound` verdicts should be read as provisional.** The correct summary
of this release is not "the instruments are trustworthy" but "we now know which
ones were not, and have a method for finding the rest."

## What this line found about its own review process

RFC-0.24-001 predicted it would partly be an audit of the review process, since
most of the eleven prior instances had passed through architect review
uncaught. That bore out, on both sides:

| Found by | What |
|---|---|
| Implementer | The architect's `grep "^publish = false"` premise — whitespace-brittle, ten false negatives |
| Implementer | The architect widened E-013 in `ERRATA.md` and not in its paired `v1-limitations.md` |
| Implementer | The audit totals table stating 56 while summing to 54 |
| Architect | `ci-proptest` certified `sound` while running zero tests |
| Architect | Gate 4 — his own Pass 1 verdict — resting on proxy attestation |
| Architect | A crate count taken against a population including two non-members |
| Architect | His own sizing of the ABI repair, wrong by three defects, after recommending it to the owner |

**Neither side caught its own.** That is the strongest practical result of the
line, and an argument for the review boundary rather than against either party.

## Scope discipline, reported rather than smoothed

The pre-cut repair group was declared final at four items, then seven, then an
eighth became its own RFC, which then grew an R6 in review. Two of those three
extensions were justified by new severe findings and the fourth was the
anticipated branch of an acceptance criterion — but **"this is final" was wrong
every time it was written.** RFC-0.24-001's own risk register predicted exactly
this, and the prediction is more useful than the reassurance.
