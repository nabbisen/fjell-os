## What this release is

Three RFCs, **four errata closed** (**E-037**, **E-040**, **E-041**,
**E-042**), and one crate deleted.

0.30 found instruments reporting success without having checked something.
**0.31 found instruments that had never executed at all**, and the reporting
that covered for them. A smoke runner that accepted six milestones nothing
could pass. A CI with one green run in 152 that had never once compiled the
kernel, while eleven documents said it ran on every push. A compiler ten
months and seven minor versions stale behind a floating channel.

**CI built this product for the first time in this release.** That is the
release's single most consequential change, and it is why two of this cut's
exit criteria did not exist at the last one.

## The repro-baseline diff

**Three digests moved**, and **not the one every previous cut moved.**

| Binary | Size before | Size after | Bytes differing |
|---|---|---|---|
| `fjell-auditd.bin` | 2760 | 2760 | 1282 (46%) |
| `fjell-init.bin` | 17223 | 17223 | 4815 (27%) |
| `fjell-netd.bin` | 831 | 831 | 72 (8%) |

`fjell-neg-test.bin` **did not move** — and it is the only binary that moved
at 0.24.0, 0.27.0, 0.28.0, 0.29.0 and 0.30.0, and what the cut handoff said to
expect. The two sets are disjoint.

**Why this is the expected set anyway.** All three are byte-identical in
*size*; only their contents shifted. That is `-C metadata` symbol-hash churn —
the workspace version feeds `-C metadata`, which changes symbol hashes and
therefore constant pools and relocations without changing layout. This
project has hit it before: RFC-v0.16-005 H-04 recorded `-C metadata` moving
digests on a version bump, and RFC-0.30-001 used exactly that mechanism to
demonstrate the repro check's sensitivity.

**Which binaries are metadata-sensitive is a property of the compiler**, and
the compiler moved seven minor versions in this milestone. This is the first
version bump under 1.98.1, so the membership changing is expected in kind
even though the specific set is new. Re-derived and reported rather than
absorbed, as the cut handoff required.

**The baseline's `# toolchain:` header did not change**, and must not have:
`1.98.1 / 48a229ceaefd4985c50990b14116b6d856af0985 /
x86_64-unknown-linux-gnu / LLVM 22.1.8`. The compiler did not move at this
cut — only the version did. A moved header here would have meant the rebuild
did not happen under the toolchain it claims.

## What shipped

### RFC-0.31-001 — six milestones the smoke runner accepted and nothing could pass

`cargo xtask qemu-test` accepted `m1`–`m6` and burned a 60-second QEMU
timeout on each. The kernel emits no `TEST:M1..M6:PASS` marker and never has;
`TEST:M7:PASS` is the cumulative pass for everything they once covered. The
runner's accepted list and the kernel's emitted markers had drifted with
nothing comparing them.

One list now, and a test reads `crates/fjell-kernel/src/trap/dispatch.rs` and
fails in **three** directions: an accepted milestone not emitted there,
something emitted that is not accepted, **and a marker built in a way the
parser cannot read** — so "invisible" cannot pass for "absent". `qemu-test m5`
answers in 0.36s naming the five milestones that can pass.

Closes **E-040**.

### RFC-0.31-002 — a CI that builds the product

No CI job had ever compiled the kernel or a service. Every job targeting
`riscv64gc-unknown-none-elf` died at:

```
error: "/usr/lib/rust-1.91/lib/rustlib/src/rust/library/Cargo.lock" does not
exist, unable to build with the standard library
```

Ubuntu's apt `rust-src` ships the standard library's source without its
`Cargo.lock`; every kernel build passes `-Z build-std`. No apt package fixes
it, so seventeen hand-copied install blocks had been installing a toolchain
that structurally could not compile this product since the first QEMU job
existed.

CI installs through rustup from `rust-toolchain.toml` via one composite
action that **fails closed** when the file is absent — rustup would otherwise
resolve to the runner's ambient `stable` and go green against a toolchain
nobody declared, which was RFC-0.30-003's objection and was correct.
`ci.yml` now carries zero versioned toolchain mentions, and
`toolchain-declarations` was inverted to enforce that, **deriving the set of
jobs that need a toolchain from their own `run:` lines** rather than from a
list of job names.

Three further defects, each invisible until the one in front of it stopped
failing: `ld.lld` had never been installed by any job; `ci-test-v07-formats`
passed no `crypto-profile-development` feature, named by RFC-0.29-001 and
left; the six dead `qemu-smoke` matrix entries went. `ci-proptest` needed no
fix — it had been compiling and running **24 passing property tests** all
along, then dying in its doc-test phase because the apt shim covered `rustc`
and `cargo` but not `rustdoc`.

**Eleven documents claiming a check "runs in CI" were corrected.** Exit
criterion 9 exists because of this line.

Closes **E-041** and **E-037**'s consolidation survivor.

### RFC-0.31-003 — a toolchain that is current, and stays that way

`channel = "1.91"` floated within `1.91.x` and resolved to a 2025-11-07
compiler: ten months and seven minor versions behind stable, a gap nobody had
decided on. Pinned exactly at **1.98.1**.

Verified by behaviour, not compilation: all 24 tiers green on the rebuilt
tree, plus a fully green CI run. The toolchain bump moved 24 of the 29
prebuilts — the five that did not are 32–54 byte stubs.

`quick-start.md` was still telling every first-time reader to
`apt install rustc-1.91`: simultaneously E-041's cause, live in the one
document written for someone who has never built this project, and the last
thing in the tree that would have collided with an exact pin. It uses rustup
now, and an apt Rust-toolchain instruction in any live documentation site is
a gate failure.

An exact pin converts silent drift into silent staleness, so exit criterion
10 exists: the cut records the gap, and more than three minor versions behind
blocks the tag. `rust-version = "1.91"` deliberately did **not** move — a
floor is a promise to a consumer — but is now verified at exactly `1.91.0`.

Closes **E-037**, the arc that opened at E-035.

### Removed — `fjell-identityd` and an orphan API module

`fjell-identityd` had never compiled for its own target since it was written.
It imports `fjell_service_api::storaged`, which lived in an orphan file no
`mod` declaration ever included, whose functions were skeletons returning
`ServiceUnavailable`. The only job that compiles the crate had never got past
installing its toolchain, so nothing could see it.

Deleted rather than wired to a stub that cannot work. The node-identity
*design* is untouched in `fjell-identity-format`, which four crates depend on.

Closes **E-042**.

## What this release does not claim

- **Cross-machine reproducibility.** Every digest ever recorded here was
  produced on one machine.
- **That CI gates the release.** It does not. Every release gate runs
  locally, deliberately; criterion 9 *records* CI's conclusion, it does not
  defer to it.
- **That the toolchain will stay current.** Criterion 10 claims only that it
  cannot go stale without a dated, signed decision in a release record.
- **A bisected MSRV.** `rust-version = "1.91"` is a verified floor.

## The implementer's own findings this cut, recorded

Both criteria that had never run before found something, which is the
argument for running them rather than assuming them.

1. **Criterion 10's own written command was wrong** — mine, from four days
   ago. Step 14 offered, as an alternative to `rustup check`:

   ```
   curl -s .../channel-rust-stable.toml | grep -m1 version
   ```

   `[pkg.cargo]` is the first section in that file, so `grep -m1` returns
   **cargo's** version: it answered `0.99.0 (797e8a9bc 2026-08-05)` against a
   real stable rustc of `1.98.1`. A cut using it would have recorded a
   nonsense gap. Corrected in `release-handoff.md` to an `awk` that selects
   `[pkg.rustc]`, verified to return `1.98.1`.

2. **Step 7 understated the work, and Gate 12 goes red in the middle of it.**
   Moving three RFCs to `done/` broke six inbound links — each handoff's
   `**Governing RFC:**` and each `§N answer` document's link — and left three
   handoff `**Status:**` lines reading `Accepted`. `doc-links` and
   `handoff-status` both caught it, *after* the move. The 0.30.0 cut did all
   of this correctly and none of it was in the procedure, so the second cut
   rediscovered it from a red gate. Step 7 now says so, including that
   `rfcs/README.md` carries **two** counts to update, not one.

3. **The repro-baseline diff did not match five consecutive cuts** — see
   above. Reported rather than absorbed.

4. **The standing handoff §3 describes the logo URLs as "pinned to `main`
   between releases".** They are not, and have not been for at least three
   cuts: they sit at the previous release's tag and are rewritten at each
   cut. The mechanism §3 describes is right; that sentence is stale.

5. **Criterion 9 cannot cover the commit that records it.** It reads the
   release commit's run, and the release record naming that run id is
   necessarily a later commit. This record cites run `34703606384` on
   `5d9d383`, which contains everything in this release except this file. The
   ordering is sound but the boundary is worth stating rather than leaving
   for a reader to notice.
