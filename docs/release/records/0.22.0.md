## Findings blocking this release

Both were surfaced by this RFC's own new or existing-but-newly-fed checks,
per the governing principle ("every gate added or strengthened... must be
demonstrated failing on a deliberately broken input") and handoff §6
("report it, do not fix it in this slice").

### Finding 1 — Gate 12 (`rfc-status-folder`): RFC-v0.17-001 status/folder disagreement

`rfcs/done/RFC-v0.17-001-trust-anchor-provisioning.md` sits in `rfcs/done/`
(the folder RFC 000 defines as "disposition is final") but its `Status:`
field still reads `Accepted (design options — requires architect
decision)` — never updated to `Implemented` or `Closed`, even though its
concrete deliverable (the `--allow-tofu-provision` TOFU flag) shipped in
v0.20.0 and is referenced as done in `docs/release/v1-limitations.md` row
6 and `rfcs/README.md`'s own RFC-v0.17-001 entry. This is precisely the
"status field that lies" anti-pattern RFC 000 exists to prevent, and
precisely RFC-v0.22-001's motivating pattern (a gate reporting green, or
in this case simply never having been asked, while a documented rule went
unmet) — now caught mechanically for the first time by the
`rfc-status-folder` subcheck added in Slice 4.

**Not fixed here.** Correcting this requires an architect/owner decision
on RFC-v0.17-001's true current status (`Implemented`? Does the file need
an update to reflect the shipped TOFU-flag subset while leaving the rest
of its design-decision scope open, i.e.
`Implemented-with-Errata`?) — a substantive RFC-content judgment, not a
mechanical fix.

### Finding 2 — Gate 7 (`ERRATA register`): new erratum E-012 is OPEN

Slice 4 recorded erratum **E-012** in `docs/rfcs/ERRATA.md` per RFC scope
item 5 (the v1.0 release checklist's Step 9 references
`target/release-bundles/*.bundle`, which `package_release.rs` never
produces). It is marked `OPEN` — not `ACCEPTED` — because declaring it a
deliberate, accepted limitation is a judgement call for the owner, not
something to self-declare while adding the entry. Gate 7 (unchanged,
pre-existing code) correctly fails on any `OPEN` erratum; this is that
gate working as designed against newly-recorded real data.

**Not fixed here**, per the RFC's explicit non-goal: "Not a v1.0 checklist
executability audit... the Step 9 finding is recorded in ERRATA instead."
v1.0 is not in view for this RFC or this release; **this finding does not
block a v0 release on its substance** — only Gate 7's blanket "0 OPEN"
rule, which does not distinguish v0-relevant from v1.0-only errata, is
what turns it into a release blocker here. Resolving that is itself a
Gate 7 design question for the architect, not something to route around
unilaterally.
