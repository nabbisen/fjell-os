## What this release is

**The first release in which a person can put something into this system and a
service receives it.**

0.24 was about whether the project's own evidence could be believed. 0.25 is
the owner's directed return to functional advancement, and it went to the place
both chosen themes — service plane and human operability — turned out to be
blocked on.

Before this line the kernel decoded **no external interrupt at all**. `scause`
cause 9, `SupervisorExternal`, was not a `TrapKind`; it fell through to
`Other(scause)`, which its own doc comment describes as logged-and-ignored in
user mode and **panicking in kernel mode**.

Above that absence sat a complete, documented design — three syscalls whose
doc-comments described PLIC claim/complete semantics, an `Interrupt` capability
kind, rights named in prose, and a shipped driver whose entire receive loop was
written against them. **`fjell-driver-virtio-net` had been calling
`sys_irq_bind` since v0.4, receiving `UnknownSyscall`, printing "IRQ bind
failed" and exiting.** It had never once got past its own initialisation.

This release supplies the floor. It does not add a subsystem.

### The repro step, this time as procedure rather than discovery

The 0.24.0 cut hit a red tier 5 and had to diagnose it from scratch: the
workspace version is a build input via Cargo's `-C metadata`, so bumping it
changes emitted artefacts with no source change. That was written into
`docs/src/release/v0-release-cycle.md` as a step before criterion 4.

**This cut followed it.** Determinism confirmed first — two builds at `0.25.0`
produced the same digest — then the baseline re-recorded and the result
verified:

```
$ git diff --numstat tests/repro/baseline-digests.txt
1       1       tests/repro/baseline-digests.txt

$ cargo run -p fjell-repro-check -- --skip-build
fjell-repro-check: PASS (29 artefacts identical)
```

One line, one binary, the same `fjell-neg-test.bin` as last time. **A procedure
gap found in one release and closed in it turned a red tier into a checklist
item in the next.** That is the only evidence that writing it down worked.

**Seven demonstrations, all in QEMU** — because `fjell-kernel` has no `[lib]`
target (E-013), none of this is host-testable, and every claim in it cites a
serial log rather than a test run. This is the first release where that
recorded limitation constrained the work rather than merely being disclosed.

### The two design changes made mid-flight, and why they are right

The implementer's first version completed each PLIC claim synchronously inside
the trap handler. In QEMU it stormed continuously and the driver never ran.

**Completing a claim before the driver has cleared a *level-triggered*
condition re-arms a line that is still asserting.** Completion belongs in
`sys_irq_ack`, after the driver has read `RBR`. The unbound path follows from
the same fact: it leaves the source claimed — which *is* the PLIC's own masking
mechanism, not a second one — and `sys_irq_bind` completes any outstanding
claim on the source it binds.

Both storms were found by running, not by reasoning, and the implementer
doubted the fix. The doubt was reasonable; the hardware requires it.

### RFC-0.25-002 — the RFC lifecycle policy

The 5-folder variant adopted, and an RFC 000 that **states
folder-as-source-of-truth** — a rule `rfcs/README.md` and
`rfc_status_folder.rs` had both been citing it for while it mentioned folders
zero times. `rfc-status-folder` now reads three folders and narrows `proposed/`
to `Proposed` only, demonstrated failing in both directions before being
trusted.

### E-018 is the one to read

`task::scheduler::PRIORITY_USER` is 32. `task/spawn.rs` has a **local**
`const PRIORITY_USER: u8 = 2` used for every service spawned through `spawn()`.
`sys_task_start` hardcodes a third `2`. `priority_to_bucket` puts 2 and 32 in
different ready-queue buckets and the scheduler always drains the higher first,
so **`init` preempts every other spawned task whenever both are ready.**

It was invisible until now because every prior `init` path that waits on a
service uses a **blocking** recv, which removes `init` from ready-queue
contention entirely and sidesteps the defect by construction. RFC-0.25-001's
`init` needed a non-blocking poll — a blocking wait would hang every profile
that never types anything — and that poll starved `driver-uart` completely.

Correcting the constant **hung the M6 boot sequence** and was reverted rather
than chased. Something already shipped depends on today's ordering in a way
nobody yet understands. A narrow `image_id`-keyed stopgap covers `driver-uart`
alone — acceptable only because it is keyed on *identity* rather than table
position, which is the defect class RFC-v0.23-002 spent a milestone removing
from milestone markers.

**Its own RFC is the next line** (owner decision, 2026-08-16).

## Accepted risk

**The instruments are unchanged since 0.24.0, and 33 of their findings remain
open.** This release was certified by them. That is the cost the owner accepted
when deprioritising stability work in favour of functional lines, and it is
disclosed rather than assumed: E-014 through E-017 are all carried forward
untouched, and the audit's 22 `sound` verdicts remain **provisional** because
the re-derivation E-017 requires has not been done.

Two further things this release should be read alongside:

- **Nothing in the interrupt plane is host-testable.** Seven demonstrations,
  seven QEMU logs. If a lost-wakeup bug exists in the check-then-block window,
  QEMU timing is unlikely to expose it and no unit test can.
- **`driver-virtio-net` now fails one layer further along.** It gets past
  `sys_irq_bind` for the first time since v0.4 and then fails for an honest
  reason — nothing ever populated its `CAP_IRQ` slot. Recorded, not chased.
  The network receive path still has never executed.

## What this release does not claim

It does not make the project **usable**. There is no shell, no command set, no
line editing, no echo policy. A byte reaches a service and stops there, which
is exactly the boundary RFC-0.25-001 drew and held.

The distinction the RFC made — *interactive, not usable* — is the honest
summary of what changed.
