# Proof-Review Re-Run — Verus prover upgrade (v0.21.3)

**Date:** 2026-07-30
**Performed by:** architect
**Reason:** `TOOLCHAIN.lock` requires a recorded proof-review re-run before the
pin may be updated. This is that record.

## Why the pin changed

The pinned prover (`release/0.2026.05.24.ecee80a`) was installed by unpacking a
release zip to `~/tools/verus` and putting it on `PATH` by hand. The owner
objected that a hand-placed binary is untracked, unupdatable, and rots — a fair
maintainability objection, and consistent with this project's general preference
for managed installs.

The Arch/CachyOS AUR package `verus-bin` is package-managed, self-contained
(bundles its own z3), and declares `Provides: verus`. Its version is
`0.2026.07.27.31579f0` — roughly two months newer than the pin. Adopting it
therefore required re-certifying the proofs under a different prover.

No proof source was modified. No obligation was weakened, removed, or given an
additional hint. The proofs were re-checked exactly as written.

## What this evidence is worth

This is **stronger** evidence than the original certification, not merely
equivalent. The obligations were discharged by a different prover build, across
a two-month release gap, on a different rustc (1.97.1 vs 1.95.0), on a different
host OS (CachyOS vs Ubuntu 24.04). Surviving that is the kind of robustness the
RFC-v0.17-005 two-milestone promotion criterion was reaching for and — as
RFC-v0.18-001 conceded in its "honest caveat" — did not really get, because both
recorded PASSes came from a single development session.

That caveat is now materially weaker. It is not fully closed: this is still a
prover change rather than intervening development churn in the proved code.

## Environment note

`verus-bin` requires rustc `1.97.1-x86_64-unknown-linux-gnu`, which the pinned
prover did not. Installed via `rustup toolchain install`. This remains
independent of the Fjell build toolchain (`rust-toolchain.toml`, channel 1.91) —
Verus is still never a Fjell build dependency, and ordinary contributors are
unaffected.

z3 is **unchanged at 4.12.5**, now bundled at `/opt/verus/z3` by the package
rather than unpacked by hand. The SMT backend is therefore constant across this
upgrade, which narrows what changed to the Verus front end and its rustc.

## Gate behaviour observed — worth recording

`verus-check --release-required` **correctly refused to certify** while the
detected version differed from the pin:

```
verus-check: BLOCKING — --release-required requires the pinned Verus version
(see TOOLCHAIN.lock). Certify proofs under the pinned version or update the
lock with a recorded proof-review re-run.
exit 1
```

That is the H-04 fail-closed behaviour working as designed: passing proofs were
*not* sufficient to certify a release under an unrecorded prover. The gate
demanded this record before it would go green. Noted because it is a rare
instance in this release line of a mechanical check refusing to accept a
plausible-looking green — the opposite of the pattern found four times
elsewhere.

## Disposition

`TOOLCHAIN.lock` updated: `release`, `channel`, install source, `host_os`, and
`last_success_date`. Recorded results unchanged at 20 verified, 0 errors.

The previously pinned prover remains valid; nothing about the old certification
is retracted. This records that the same obligations hold under both.
