# Proof-review re-run — prover `0.2026.07.27.31579f0` → `0.2026.11.02.8bf68ee`

**Architect, 2026-11-11.** Recorded **before** `TOOLCHAIN.lock` was moved, as that file requires:
*"Update only with a recorded proof-review re-run."* Follows the standard set by
[`v0.21.3-prover-upgrade.md`](./v0.21.3-prover-upgrade.md).

**Scheduled by the owner** on 2026-11-09, as 0.42-004, after the AUR package overshot the pin and
0.41.0 had to be cut with a hand-installed prover (E-109).

## What changed

| | before | after |
|---|---|---|
| Verus | `release/0.2026.07.27.31579f0` | **`release/0.2026.11.02.8bf68ee`** |
| rustup toolchain | `1.97.1-x86_64-unknown-linux-gnu` | **`1.99.1-x86_64-unknown-linux-gnu`** |
| **z3** | **4.12.5** | **4.16.0** |

**The solver changed, and that is the material difference from the last upgrade.** The v0.21.3
record could say *"z3 is unchanged at 4.12.5"*; this one cannot. z3 is what actually discharges the
obligations, so a solver version is the likeliest single cause of a proof ceasing to verify —
different heuristics, different incompleteness, different timeouts. **0.42's scope said in advance
that z3 being unchanged was not an assumption to carry forward**, and it was right not to.

The prover reports `Toolchain: 1.99.1 … (overridden by environment variable RUSTUP_TOOLCHAIN)`.
`RUSTUP_TOOLCHAIN` is **unset** in the environment; Verus's own launcher sets it. Both `1.97.1` and
`1.99.1` are installed, so the toolchain the new prover wants is present.

## How it was run, and why in a scratch tree

`verus-check` compares `verus --version` against the lock's `release` and **fails closed** on a
mismatch — correctly. So with the new prover installed and the lock still pinning the old one, the
gate refuses to run the proofs at all. The re-run was therefore done in a **scratch git worktree**
with the lock's `release` advanced, so that nothing in the committed tree asserted the new prover
before this record existed. The worktree was removed afterwards.

## A finding, recorded here because this upgrade is what exposed it

**`TOOLCHAIN.lock` pins z3 and nothing checks it.** `verus_check.rs:85`'s own comment says it will
*"print detected Verus/z3 versions and compare against the pinned TOOLCHAIN.lock release"* — it
detects and compares **only the Verus release**. There is no z3 detection and no z3 comparison.

So **z3 moved from 4.12.5 to 4.16.0 across this upgrade and no gate noticed**, while the lock
records the z3 version as part of a reproducibility pin. The pin is documentation, not enforcement.
That is filed as an erratum rather than fixed inside this record.

The lock's `[z3] path = "/opt/verus/z3"` is also machine-specific: it was accurate for the AUR
package and is not for a hand-install (`~/.local/share/verus/z3` here). The authority on what ran
is `verus --version`'s own report, not that field.

## What this record does not claim

- **That the new prover is better, or that the proofs are stronger.** Only that the same twenty
  obligations, unmodified, verify under both.
- **That z3 4.16.0 was compared obligation-by-obligation against 4.12.5.** It was not; the old
  prover's directory was replaced by the install, so the old side of this comparison is the
  **recorded** result from `v0.21.3-prover-upgrade.md` and the 2026-11-09 release-required run, not
  a fresh one.
- **That any gate will notice the next solver change.** It will not — see the finding above.
