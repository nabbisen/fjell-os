# v0.23+ Direction — Options Paper

*Prepared for the joint planning discussion the owner scheduled at v0.22
completion. **This paper decides nothing.** It exists so the decision can be
made against measurement rather than impression. Every number below was
measured against the tree at `0.22.0`, not estimated.*

---

## 1. The four measurements that should drive this decision

> ## ⚠ Correction, 2026-07-31
>
> **M1 as originally written was wrong, and this paper's recommendation was
> accepted while it stood.** It claimed the renderer was "845 lines that nothing
> calls." In fact `fjell-init` calls it **13 times at runtime**, linking
> `fjell-proxy-text` as a library and rendering `StateNode`/`EventNode` values
> **in its own address space**.
>
> The cause of the error is worth recording: `init/src/main.rs` contains two NUL
> bytes inside a legitimate NUL-padded byte literal (`*b"release-m8-dev\0\0"`),
> so GNU grep classifies the file as binary and **silently suppresses every
> match**. The measurement tool reported nothing and looked like a clean result.
>
> **The corrected finding is sharper, not softer.** The renderer is not unused —
> it is used *on the wrong side of the boundary*. `init` is simultaneously the
> emitter and the renderer, which is exactly what ABDD forbids. The serial
> output that resembles an ABDD demonstration is an ABDD violation.
>
> The recommendation is unchanged and, if anything, strengthened: the work is
> still the smallest of the four directions, and it now also *removes a standing
> architectural violation* rather than merely adding a demonstration. Sizing
> revised from ~100–150 lines to ~200–300, since `init`'s 13 render call sites
> must become emissions. See `RFC-v0.23-001`.

**M1 — Fjell's headline demonstration is written and unwired.**

`fjell-proxy-text` contains **845 lines** of working renderer — 29 functions,
including `ingest()`, severity/status labelling, a scroll ring, pinned
criticals, rate limiting. Its entire service entry point is:

```rust
pub extern "C" fn service_main() -> ! {
    sys_debug_writeln("M5: proxy-text started");
    sys_exit(0)
}
```

`fjell-semantic-stream` is the same shape. The two halves of "applications emit
meaning, a proxy renders it" both exist and have never been connected.

**M2 — The round-trip data model already exists.**

`fjell-semantic-format` defines `ActionId`, `ActionSpec`, `ActionKind`,
`ActionRequest`, `ActionResult`. The proxy→OS operation-request path — the part
of the M7/M8 completion criteria that says *"the proxy can return an operation
request, that request is capability-checked"* — is fully modelled. Only the
runtime is absent.

**M3 — A working service is about 35 lines.**

`fjell-recoveryd` is the minimal live example: `send_ready()`, then
`loop { recv_call(); match tag { … reply(…) } }`. That is the entire per-service
wiring cost. Twelve of 29 services follow it; **17 do not receive IPC at all.**

**M4 — There is no console input path anywhere.**

No `uart_read`, no `getchar`, no read syscall — not in `fjell-kernel`, not in
`fjell-syscall`, not in any service. Output-only.

This is the single most decision-relevant finding in this paper, and it is
explained in §4.

## 2. Direction A — Make the semantic plane real

*The ABDD live path: a service emits intent, the proxy renders it, the proxy
returns an action request, the kernel capability-checks it.*

**What exists:** the renderer (845 lines); the format including the full action
round-trip (M2); the frozen v1 intent catalog; both service binaries built and
embedded in the kernel image (`SEMANTIC_STREAM_BIN`, `PROXY_TEXT_BIN`); both
`ImageId` constants (6, 7); both debug-name table entries.

**What is missing, exactly:**

| Gap | Size |
|---|---|
| `ep_obj` match arms in `spawn.rs` — both currently fall through to `_ => 0` | 2 lines |
| `init` spawns neither service | a few lines |
| `semantic-stream` service loop | ~40 lines, recoveryd pattern |
| `proxy-text` service loop calling `renderer::ingest` | ~40 lines |
| An emitter — some service actually emitting an intent node | small |

**Sizing: ~100–150 lines plus wiring.** This is the smallest item in this paper
by a wide margin, and it is small *because* nine release lines of work already
built everything around it.

**Dependencies: none.** Does not require B, C, or D.

**Claim it enables:** *"Fjell separates meaning from rendering, and here it is
doing that."* Today the project's distinguishing architectural bet is
demonstrated only by unit tests. This is the difference between a design
document and a running system.

**Risk:** the demonstration may reveal that the ABDD boundary needs design
changes the renderer's unit tests never exercised. That would be a genuinely
useful finding, but it could turn a small line into a medium one.

## 3. Direction B — Make the service plane real

*Wire the 17 services that never receive IPC.*

**What exists:** all 17 build, are embedded, and start. Several have substantial
internal logic behind an entry point that exits.

**What is missing:** the ~35-line loop per service, plus endpoint and spawn
wiring. Some — `storaged`, `devmgr`, the virtio drivers — additionally need real
device work behind the loop, which is a different order of effort from wiring.

**Sizing: medium to large, and unevenly distributed.** Wiring is cheap; making
`storaged` genuinely store and `devmgr` genuinely enumerate is not.

**Dependencies:** partially subsumes A (the semantic services are 2 of the 17),
but doing A alone is far cheaper than doing B to get A.

**Claim it enables:** *"the service plane runs"* — real, but diffuse. No single
demonstration follows from it.

**Assessment:** highest effort-to-claim ratio of the four. Worth doing
eventually; poor value as the *next* theme, because it buys breadth rather than
a demonstrable property.

## 4. Direction C — Make it operable by a human

*Base userland, FR-SVC-006: list, read, write, inspect, audit read, config
validate.*

**This one is not what it looks like.** It reads as userland work. It is
kernel work first.

Per M4, **there is no input path at any layer.** A human-operable system needs,
at minimum: UART RX in the kernel, an interrupt path for it, a read syscall, and
a console service to own it. That is **new kernel surface and a new syscall** —
in a project that currently has 9 declared-but-undispatched syscalls whose
disposition is still an open question, and whose discipline has been to avoid
growing the kernel.

**Sizing: large, and larger than it appears.** The userland commands themselves
are the easy half.

**Dependencies:** requires the kernel input path. Interacts with the open
syscall-disposition question — you would be adding syscalls while nine existing
ones remain undecided, which argues for settling that first.

**Claim it enables:** *"an operator can sit down and use it."* Strong claim,
genuinely tied to "production readiness."

**Assessment:** the right long-term goal, wrongly sized by intuition. If this is
wanted, the honest first step is a scoped spike on the kernel input path, not a
userland RFC.

## 5. Direction D — Make it run on metal

*Hardware bring-up, StarFive VisionFive 2.*

**What exists:** a board profile (`platform/starfive-visionfive2/`), a deployment
document, and the arch abstraction. **Never booted on silicon** — errata E-004,
ACCEPTED as a v1.0 limitation.

**Sizing: large, and the least predictable in this paper.** Hardware bring-up
fails in ways that cannot be scheduled.

**Dependencies:** none strictly, but it consumes the most attention and would
stall every other direction while it runs.

**Claim it enables:** the strongest available — *"it runs on real hardware."*

**Assessment:** the roadmap already places this at v2+. Nothing measured here
argues for moving it earlier, and the unpredictability argues against taking it
while other directions are cheap.

## 6. Cross-cutting alternative — the v0.23 quality candidates

Not a "direction" but a real option: another consolidation line.

Seven recorded candidates: ACCEPTED as an unguarded escape hatch; the 9
undispatched syscalls; build-output determinism; negative-coverage completion
(store/upgrade/svc); DMA user-VA unmap; v1.0 checklist executability;
`.gitignore` gap for `tests/runs/` and `tests/qemu/artifacts/`.

**Assessment:** v0.22 was a consolidation line and it earned its place — it
caught two real defects while being built. But the owner has stated that
functional advancement must precede v1.0 consideration, and a second consecutive
quality line would not serve that. **Two of these are worth folding into
whichever direction is chosen** rather than run standalone: the syscall
disposition (if C is chosen, since C adds syscalls) and the `.gitignore` fix
(trivial, and it currently makes the release cycle's own entry criterion
unsatisfiable).

## 7. Dependency map

```text
A (semantic plane)  ──────────────────────────►  independent, ~100–150 lines
                                                 
B (service plane)   ──── contains A ──────────►  medium–large, diffuse claim

C (human operable)  ──── requires ────────────►  kernel input path (new syscall)
                              │
                              └── interacts ──►  9-syscall disposition (open)

D (hardware)        ──────────────────────────►  independent, large, unpredictable
```

Only A is both independent and small. C's dependency is invisible until measured
— which is why it is stated here rather than discovered mid-line.

---

## 8. Recommendation

**Lead with A. It is not close.**

It is roughly one-tenth the size of any alternative; it depends on nothing;
and it produces the one claim this project cannot currently make — that its
distinguishing architectural bet actually runs. Nine release lines of
infrastructure already exist behind it, unused. The measured gap is two match
arms, two service loops, and an emitter.

It also directly answers the owner's stated concern about "playful
attractiveness": after A, Fjell can be *shown* rather than described.

**Then C, entered honestly** — beginning with a kernel input-path spike, not a
userland RFC, and after the 9-syscall disposition is settled so the kernel
surface question is answered once rather than twice.

**B opportunistically**, service by service, as each is actually needed.

**D when it is deliberately chosen**, with the understanding that it will
dominate whatever line it lands in.

**One caution.** This project's discipline is thin *verified* vertical slices,
and A is the first line in a while that would add runtime behaviour rather than
documentation or tooling. It should ride the same cycle — RFC, slices, evidence,
gates — and not be treated as a demo exempt from them. The v0.22 gate work makes
that cheaper than it has ever been, which is an argument for doing the function
work now rather than later.
