## What this release is

Four lines, **seven errata closed** (E-091, E-105, E-106, E-111, E-113, E-114, E-115),
two filed and carried forward as accepted limitations (E-110, E-112), and one restated
after three wrong framings (E-093). User space can read a clock. `storaged` writes to
the sector `init` asked for. Binding a capability to a lease needs a right no blanket
grant carries. The Verus prover is pinned to a current release.

**Four of the seven closed errata were defects in the measuring apparatus, not in the
product** — a release gate blind to seven of eleven harness markers (E-111), a
reproducibility pin that never checked the solver (E-112, filed and deliberately left
open), CI pinning one action at two majors while four targeted a removed runtime
(E-113), and the register asserting as live four defects it had recorded as closed
(E-114). None of those changed a line of the kernel.

## What shipped

### RFC-0.42-001 — every capability has a revocation path, and the premise that says so is enforced (closes E-091)

`sys_cap_bind_lease` let a `LeaseAdmin` holder bind an unbound capability to any `Active`
lease, including one it did not own, because `RFC-v0.7.4-003`'s `LEASE_BIND` right and
lease-scope check **were never built**. `CapRights::LEASE_BIND` now exists at bit **30**
— the done RFC specified `1 << 25`, which belongs to `REBOOT`, and moving a shipped bit
is an ABI break — **in neither rights aggregate**, so a blanket grant does not confer it.
Binding requires `LEASE_CREATE` *and* `LEASE_BIND` on the same capability and refuses a
lease the caller does not own, auditing the refusal as `lease.bind_rejected` (`0x0604`).
The implemented rule is **deliberately narrower than the document it came from**, whose
own clause permitted everything. Two amendments corrected the architect: Amendment 1
withdrew R3/R4 as written, Amendment 2 removed E-093 from the line.

### RFC-0.42-002 — user space can read a clock, and the timer stays dormant (closes E-106)

`sys_clock_now_ns` (syscall **113**; `120` stayed retired) returns a monotone nanosecond
counter, gated on a new `Clock` kind and `CapRights::CLOCK_READ` at bit **31**, in neither
aggregate and granted by name to `storaged` alone. The design turned on a separation the
erratum had not drawn: the kernel's timer machinery was already written and wholly
dormant, because `enable_interrupts()` has zero callers. Reading a counter needs no
interrupt, so the line exposes the counter and **leaves `STIE` masked**. **One premise of
the RFC was wrong and the implementer said so:** the counter was not already readable —
CLINT is unmapped and `mcounteren` unset — so they used the `time` CSR with
`mcounteren.TM` only, a boot change the RFC had not named and smaller than mapping CLINT
into every task.

### RFC-0.42-003 — `storaged` writes where it is told (closes E-105)

A **wire-format disagreement**, not a `storaged` bug: `init` sends
`WRITE_BEGIN(lba_lo, lba_hi)` with the low half in its first data word, and `storaged`'s
only caller bound that word to `_badge`, so every write landed at sector 0 and each chunk
lost 8 bytes of every 32 while `init` printed `block write ok`. The fix **removes the
opportunity to misname the word** rather than renaming it: both ends share one
encode/decode in `fjell_service_api::storaged`. `init` also stops discarding seventeen of
its eighteen replies, which is why nothing had noticed.

### 0.42-004 — the prover pin catches up (files E-112)

Pinned to `0.2026.11.02.8bf68ee`; all **20** obligations re-verified unchanged (8 + 5 + 7,
per-target counts identical to the v0.21.3 record), no proof source modified, and the
review record written **before** the pin moved as `TOOLCHAIN.lock` requires. **z3 moved
4.12.5 → 4.16.0**, which `verus-check` does not compare despite a comment claiming it
does — E-112, filed and deliberately not fixed inside the upgrade.

### The two small items

Limitations **row 20** closed — `run-info.txt` and the evidence provenance now record the
emulator version. And **E-113**: seven GitHub action pins moved off the removed Node 20
runtime, where the 0.42 scope note had recorded one.

## What this release does not claim

- **No security advisory.** The kernel has never been distributed as a runnable artefact
  and the product has not been placed on the market. One advisory *was* handled this
  cycle and it is not Fjell's: **E-115** closed `RUSTSEC-2026-0486` against `rustix`,
  reached only through `tempfile` ← `proptest` in three leaf crates that nothing depends
  on. It touches neither published crate, the kernel, nor any prebuilt.
- **No way to block on time** (row 18). A service that wants to wait still spins or
  yields; `storaged`'s budget is still 500,000 poll rounds, now merely *reported* in
  nanoseconds.
- **Nothing reads the store back** (row 17), and the `store` tier is still NOT-GATED.
  Row 17's second closing condition was met by host tests rather than by the tier, which
  is recorded rather than slid past.
- **A boot can create at most 32 leases, ever** (row 21, E-110) — slots are never
  recycled, about nine are spent in a normal boot, and `create()` fails closed.
- **The z3 pin is recorded and not enforced** (row 22, E-112).
- **Authority cannot be withdrawn from a task without ending it** (row 12, E-093).
- **Hardware, multi-hart, POSIX, kernel-IPC, ZeroizeOnDrop and trust-anchor
  provisioning** remain as rows 1–6 state.

## The architect's own findings this cut, recorded

Four, because a record that lists only the gates' findings and not the cutter's is the
failure mode this project exists to remove.

1. **The cut commit `a130ace` landed red.** It moved the three RFCs to `done/` and
   committed **none of the Status-line edits**: `git mv` stages the rename when it runs,
   the `sed` came after, and nothing re-staged the content. Git said so in its own
   output — `rename (100%)`. **What let it through was the check, not the edit:** staging
   was verified with `git status --short | grep -av '^[MARD]'`, and an unstaged edit to a
   staged rename is reported `RM`, which starts with `R` — so the filter deleted the one
   line it existed to find. Running `handoff-status` afterwards passed and proved nothing,
   because the gate reads the working tree, which already had the fix. Confirmed red by
   running the subcheck against `a130ace` in a scratch worktree. Fixed forward in
   `fe30ad6`; **the tag does not go on `a130ace`**.
2. **E-116's first draft was wrong about its own central claim.** It asserted that
   nothing checks `README.md:22`. `version-currency` does, and running it is what found an
   **eighth** version string — the shields.io badge at `README.md:9`. `readiness-summary`
   covers the readiness heading and `handoff-status` covers the handoff pairing; all three
   fired at this cut. So the defect is **documentation, not enforcement**, which is the
   sharper reading: a reader following only the written procedure produces a tree that
   four subchecks reject, and the written cut is what gets handed to an implementer. The
   one case no gate catches is a *wholly skipped* `accepted/ → done/` move.
3. **Both wrong readings came from grepping the procedure instead of running the
   instrument that owns the question** — `consistency-check --all` after a version bump,
   which names every one of them. That is this project's own rule about a text match being
   a hypothesis, broken twice in one day by the person who wrote it down.
4. **Criterion 5 was first measured under concurrent `cargo` invocations** of mine
   (`readiness-summary`, `readiness-check`). Cargo's target lock makes corruption
   unlikely, not impossible, and a release criterion measured under concurrent builds is
   not a clean measurement. It was **re-run alone** on the committed tree, and the row
   above cites the clean run (`tests/runs/20261111-113836`). Both runs agreed: 32 PASS, 0
   FAIL, 1 NOT-GATED.
