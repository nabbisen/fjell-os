## What this release is

Three RFCs, two review fix-forward rounds and one row correction; **three errata closed**
(**E-092**, **E-094**, **E-100**) and **three filed**, all ACCEPTED and tracking 0.41
(**E-101**, **E-102**, **E-103**). `attestd` signed a record claiming three verifications nothing
performs, over five literal digests and a chain head it had never read. The three flags now read
`false`, the digests nothing computes are zero behind an availability flag the encoder zeroes, and
the measurement section is the chain's real head — read from `measuredd` through a `CALL`
capability, or disclosed as unavailable, never a stale or literal one. A lease revocation is
audited under the code the decoder knows. And the frame allocator's unit tests moved into a crate
the host can build, which immediately produced a finding (E-103).

**Two statements the cut handoff requires, as the CHANGELOG makes them.** There is **no security
advisory** (the channel exists so users of shipped software can act, and there are none):

1. **Every signed attestation record this project produced, from RFC-v0.3-004 through 0.39.0,
   asserted under a signature that a release, a rootfs and a policy bundle had each been
   verified — while nothing in the tree verifies any of them** (**E-094**). One field of the same
   class survived into review (`trust_provider_counter_supported`) and was fixed before this cut.
2. **Every lease revocation was recorded under a code the published decoder did not know**
   (**E-092**).

**What still does not hold, in the same breath:** the audit trail stops at boot (**E-102**, the
lead 0.41 candidate) — a revocation after boot, now correctly coded, is still never printed;
three of the chain's four events are placeholders and the kernel's own image is unmeasured
(**E-095**); the attestation record still carries unqualified placeholders that read as state
(**E-101**); `FrameAllocator::reserve_range` is not all-or-nothing (**E-103**); and the record is
signed by the development provider, not a hardware root. *0.40 made the record truthful; it did
not make it reach anyone.*

## The repro-baseline diff

Rebuilt before re-recording, not after (trap 2). **7 of 33** service binaries moved from the version
bump alone: `fjell-auditd`, `fjell-devmgr`, `fjell-diagnosticsd`, `fjell-measuredd`, `fjell-neg-test`,
`fjell-sample-service` and `fjell-storaged`. The baseline lines that moved are **exactly** those
seven (7 inserted, 7 deleted; compared by name against the seven `.bin` files git reported
modified). The 33 prebuilts total **168,014 bytes** (`cat prebuilt/*.bin | wc -c`), matching the cut
handoff. The subset differs each time (0.39.0's bump moved a different seven). **I did not trace why
these seven**; one thing I checked is that none of the ones I looked at (`auditd`, `devmgr`) contains
the version string, so it is not the literal `0.40.0` in the binary. The claim is that the set is the
bump's and that nothing else moved, not that I know the mechanism. *Explained in review (architect,
2026-10-29), for the next cut:* the workspace version is an input to each crate's `-C metadata` hash,
which feeds symbol mangling and codegen-unit naming and so the layout of functions in the linked flat
image — a version bump relinks every service at a different code layout, the images keep their size and
their `strings`, only code bytes differ, and a different subset moves at each bump. `repro-check` (33 artefacts
identical, PASS) verified at the new version.

## What shipped

### RFC-0.40-001 — the attestation record stops asserting what never happened (closes E-094)

`AttestationRecordV2` is built by `local` (`SCHEMA_VERSION` 2 → 3): the three `*_verified` flags are
`false`; the five digests nothing computes are zero behind an adjacent availability flag, zeroed by
the encoder; the measurement section is the chain's real head, read from `measuredd` through a
`CALL` capability (slot 4) via a shared `read_chain`, or unavailable. `ATTESTD` is out of the append
mapping in the same change. The tier asserts the record's claims against an independent host
derivation of the chain head. A review fix-forward made the rollback counter pair report whether
`attestd`'s own provider read succeeded, and what it returned. `capability-topology`: 5 / 1 / 6 →
**6 installed / 1 waived / 7 checked**; ABI 495 → **498**; unsafe 284 → **285**.

### RFC-0.40-002 — a revocation is audited under a code the decoder knows (closes E-092)

The kernel emits `LeaseRevoked = 16`; `CapDenied` (emitted by nothing) is deleted. A tier asserts the
**decoded** name `lease.revoked`. The assertion runs inside `neg-test` because `auditd` renders nothing
after boot — which became **E-102**.

### RFC-0.40-003 — the allocator's tests get a home a gate can run (closes E-100)

`fjell-frame-alloc` (`no_std`, `forbid(unsafe_code)`, `publish = false`) holds the three files; the
kernel re-exports them and every prebuilt was byte-identical. Host-lib tests 742 → **761**
(55 binaries, 1 ignored). The new tests found that `reserve_range` is not all-or-nothing (**E-103**).

## What this release does not claim

- **That attestation is real.** The record is truthful, not complete: the kernel's own image is
  unmeasured, release / rootfs / policy verification does not exist (**E-095**), and the signature is
  the development provider's keyed SHA-256 digest.
- **That the record carries no placeholder.** Keyring epochs, snapshot id and reason, health status,
  `last_advance_source` and the freshness key epoch still read as state nothing computes (**E-101**).
- **That the audit trail reaches anyone.** It stops at boot (**E-102**).
- **That frame reservation is atomic.** `reserve_range` is not (**E-103**); latent.
- **That a clean dependency check describes what Fjell OS ships.** The published crates and the
  kernel have no third-party dependencies; the check covers tools, tests and the development-grade
  crypto crate, and says so itself.
- **That CI gates the release.** Criteria 9 and 11 *record* CI; every gate runs locally.
- **Cross-machine reproducibility**, as at every previous release.

until `fjell-abi` is on the index. Neither has been uploaded; crates.io `max_version` is `0.39.0`

compressed)**, and the verification step compiled the packaged copy.

Still to be recorded here, in the completing commit: both version ids and compressed sizes read
from the crates.io API, that neither is yanked, that `fjell-os`'s verification step resolved
`fjell-abi` from the registry rather than the path dependency, and the comparison of what was
published against what was tagged — the artefact downloaded from `static.crates.io`, unpacked,
and its sources compared byte-for-byte against the tagged tree. A publish can succeed and ship
something other than what was tagged; nothing before 0.38.0 checked.

### The logo and favicon URLs

All three resolve, checked after the tag existed — they cannot resolve before it, since the tag
is the path component — with a deliberately absent path as a control, so a blanket `200` cannot
pass for a check:

```
200  .../nabbisen/fjell-os/0.40.0/assets/logo.png        (crates/fjell-os/README.md)
200  .../nabbisen/fjell-os/0.40.0/assets/logo-256.png    (html_logo_url)
200  .../nabbisen/fjell-os/0.40.0/assets/favicon.svg     (html_favicon_url)
404  .../nabbisen/fjell-os/0.40.0/assets/nope.png        (control — must not resolve)
```

*As recorded since 0.34.0: a 404 from `https://crates.io/crates/<name>/<version>` to a plain
`curl` is not evidence about a publish — the identical request against a known-live version
answers 404 too. The authoritative check is the API.*
