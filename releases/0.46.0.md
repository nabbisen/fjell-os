## What this release is

**Three lines and four small items. Three errata closed — E-011, E-110, E-125 — and one filed
(E-125, filed and closed inside the milestone).** The register stands at **124 entries, 7 accepted,
0 open**: the fewest accepted limitations this project has carried.

**0.45 made `sys_cap_install` run, and in doing so put `cap-broker` inside the kernel's trust
boundary in three places at once** — it installed a capability to an object the broker merely named,
revoked a lease the broker merely named, and handed out a lease per grant *request* from a 32-slot
table that never recycled. **0.46 takes those three bounds back.**

`consistency-check` is **25 subchecks** (23 at 0.45.0). The ABI moved **+21 items**, 524 → 545. The
suite is **35 tiers**. Host tests: lib **877**, bins **1558**. `unsafe` sites **298** — one fewer,
because deriving the install's object deleted the five-argument syscall wrapper.

**There is no security advisory.** The kernel has never been distributed as a runnable artefact and
the product has not been placed on the market.

## What shipped

### RFC-0.46-003 — the kernel bounds revocation itself (first line)

`sys_lease_revoke` **already** validated a capability's *scope* against the lease it names
(`ObjectScope::Lease(id)`). The bound existed and was **unusable for the only case that mattered**:
all four `LeaseAdmin` grants carry `ObjectScope::Any`, **necessarily**, because the leases they
revoke are created at runtime and cannot be named in a spawn-time grant. So `cap-broker`'s own
`revoke_authorised` predicate was the only thing standing between a caller and any lease in the
system — a **service-side check on the most privileged client**.

The kernel now asks **ownership**, the question `sys_cap_install` already asked of a lease it binds.
R7 becomes defence in depth and **that is shown, not claimed**: with the broker's check mutated off
the marker stays green because the kernel refuses, and **only removing both reddens it** — which the
mutation table says, rather than reporting a green it cannot explain.

**One named exception, and it is less authority than before.** An owner blocked on its own leased
capability **cannot** revoke it, so two `ipc` scenarios need a non-owner revoker.
`CapRights::LEASE_REVOKE_ANY` (bit 32, in **neither** `ALL_NON_META` nor `ALL_DEFINED` — the
`LEASE_BIND`/`CLOCK_READ` precedent) is held by `neg-test` alone, on a capability carrying **nothing
else**, with `init` getting none because it revokes no lease in the tree. **Four images could already
revoke any lease; now one can**, and `capability-topology` counts the holders — a second holder, and
zero holders, are both failures. The refusal is audited under its own kind, `0x0606`.

### RFC-0.46-001 — lease slots are recycled (closes **E-110**)

A boot could create 32 leases, ever: `create` allocated only over `Empty`, and `revoke` never bumped
the generation.

**Recycling alone would not have closed the measured defect, and the record says so because the
architect's scope said otherwise.** The 0.45 demonstration looped *request → **drop** the
capability*, and **dropping a capability does not touch its lease** — `sys_cap_drop` takes only the
`CapTable` and `cap_drop` carries the comment *"no lease check"*. All 26 leases stayed `Active`, so a
recycler of `Revoked` slots would have reclaimed **none of them**. **A per-owner quota is what closes
it:** `MAX_LEASES_PER_OWNER` = **16** of 32, refused with `LeaseQuotaExceeded`, **distinct from
`LeaseTableFull`** on RFC-0.34-002 D1's precedent for `TaskTableFull` — *the system is out* and *this
owner is out* are different answers. `cap-broker` additionally bounds a requester to **4** outstanding
grants: service policy, never the only bound.

Reclamation is **lazy — on allocation pressure, not in `revoke`** — for a correctness reason the
implementation found and the scope had not: a capability bound to a just-revoked lease must still
answer `LeaseRevoked`, and an eager reclaim would race the next `create`.

**The proof was extended, not re-verified.** `verification/verus/lease/` modelled `revoke`,
`check_active` and retire-before-wrap and **not slot reuse at all**; it now carries a `recycle`
transition and `LEASE-VERUS-008` — *the obligation the epoch cannot carry* — at **11 verified, 0
errors** against 5, and was shown **non-vacuous**: dropping the generation clause gives 8 verified, 3
errors. The demonstrations are `NEG:POLICY:ABANDON_LOOP_BOUNDED`,
`NEG:LEASE:OWNER_QUOTA_ENFORCED` and **`NEG:LEASE:QUOTA_DOES_NOT_STARVE_OTHERS`**, the last stating
the property rather than the number.

### RFC-0.46-002 — an installer derives a capability it holds (closes limitations row 26's gap)

The installer named an **integer** and the kernel built a capability to it — demonstrated at 0.45's
follow-ups by asking for object 22, `configd`'s endpoint, which installed successfully while only the
`audit` tier noticed.

Now the call **names a source capability the installer holds**, and `kind` and `object` are read from
it. **The signature went from five arguments to four**, `ecall5` was deleted with the fifth, and a
forged object is **unrepresentable** rather than rejected — the third time this project has deleted a
parameter instead of validating it, after 0.45-002's target and this line's object. Rights may only
narrow against the source.

**The price is recorded where the next author will read it:** *holding is authority.* To confer `SEND`
on object 23 the broker must hold `SEND` there, so it can now send to it. A rule conferring `RECV`,
`MINT` or `COPY` on a service endpoint would require the broker to hold that right — to take messages
out of another service's endpoint — and `endpoint-envelope` refuses any such rule until the reviewed
`BROKERED_ENDPOINTS` table says so: **the only way a rule acquires a source**. `DELEGATE_ONLY` would
be the clean form and is **not** taken, because enforcing a negative right needs one funnel for
capability checks and there is none (~20 `require_cap*` sites plus direct `rights.contains` checks);
that prerequisite is recorded for 0.47.

## Known limitations at this release

**124 entries, 7 accepted, 0 open**, every accepted erratum referenced in `v1-limitations.md`.

* **The broker now holds the authority it delegates** (row 26). The point and the price: the set it
  holds is a hand-reviewed table, and the kernel cannot express *hold for delegation only*.
* **At most 32 live leases, 16 per owner** (row 21) — the capacity that replaces *"32 ever"*.
* **The MMIO figures in release records before 0.45.0 are wrong and cannot be corrected** (row 27).
  This project does not rewrite released records, by the rule that forbids moving a tag.
* **There is still no working network** (row 25): a test environment presents a device and the driver
  reports what it read; nothing above discovery works, `sys_net_recv` exists nowhere, and the
  virtqueue logic is not linked into the image.
* **Two RFCs still say `Implemented` where the work has not shipped**, named by `rfc-evidence` every
  run, blocked on a lifecycle question **RFC 000 cannot answer**: it defines neither
  `Implemented-with-Errata`, carried by 12 RFCs, nor `Closed`.
* **The readiness matrix's "20 obligations" is a hand-maintained figure that matches nothing
  countable** — the prover's release-required total is **19** and the named ids number **17**. Found
  at this cut, recorded in the matrix, and **not** corrected: which number that row should promise is
  a judgement about what it means, and it is the owner's.

**No accepted-risk statement is written for this release.** No gate that should have blocked was left
unpassed; `pages` was transient and re-dispatched, as 0.43.0 did.
