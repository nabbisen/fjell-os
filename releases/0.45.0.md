## The first finding — a release gate that copied the definition it claimed to share

**`release-rehearsal` Gate 1 went red on a tree where `test-all`, CI and
`cargo xtask host-lib-tests` were all green.** I ran Gate 1's exact command rather than re-running
the rehearsal, and it was a **compile error**, not a test failure:

```
error: fjell-sxt-crypto requires the `crypto-profile-development` feature.
error: could not compile `fjell-sxt-crypto` (lib test) due to 1 previous error
```

**Two defects, stacked.**

1. **Gate 1 held its own hardcoded copy of the host-lib command.** `cargo_metadata::host_lib_test_argv()`
   passes `--features fjell-sxt-crypto/crypto-profile-development`, and its own doc comment calls
   itself *"the one command Gate 1 names"*. `release_rehearsal.rs` spelled
   `cargo test --workspace --lib --exclude fjell-proptest` without the feature. Two definitions, one
   claim — the **E-014 class**, and the shape 0.44 small item D and RFC-0.45-003 R6 each removed
   elsewhere.
2. **`e3fa023` — 0.45 small item A — deleted `fjell-sxt-crypto` from `secure-transportd`'s
   dependencies.** That deletion is **correct**: the release handshake is a stub and imports nothing
   from the crate. But it was the last thing in the workspace enabling that feature as a side effect
   of depending on the crate, and `fjell-sxt-crypto` refuses to compile without it by design
   (RFC-v0.7.3-002 — the development crypto profile must be acknowledged explicitly). The two copies
   had agreed only by accident.

**Fixed, not waived.** Gate 1 calls `host_lib_test_argv()`. **No accepted-risk statement is written
for it**, because the gate is not red at this tag: it passed on the re-run, and the record shows the
red, the cause and the fix rather than papering over it.

**Why nothing caught it, and what now does.** `cargo_metadata`'s existing
`test_all_and_the_release_checklist_use_the_shared_definition` read `test_all.rs` and the release
checklist **document** — but never `release_rehearsal.rs`. The one consumer it did not read was the
one that had drifted. It now asserts the rehearsal references `host_lib_test_argv()` and does not
spell `"--lib"` itself. Checking a document was not enough; **the gate is code.**

**It cost a full re-run of criteria 4, 5 and 6**, because the fix changes a host tool. That is the
right price and it is recorded so the next cut knows the shape.

## The second finding — a release gate whose headline number was 91% other people's trees

**The release suite reported 490 MMIO sites where the previous run reported 449, on a tree with no
source change between them.** The difference was a scratch clone I had made minutes earlier for the
clean-clone check, sitting under `.git-exclude/tmp/`. Measured rather than reasoned about:

| Tree | `total MMIO sites` |
|---|---|
| working tree, my clean clone present | **490** |
| working tree, clone moved outside the repository | **449** |
| **pristine clone of the same commit** | **41** |

`490 − 449 = 41`, exactly one pristine copy's worth, which is what confirms the mechanism rather
than merely suggesting it.

**So this project has 41 MMIO access sites.** The **449** is 41 real sites plus roughly 408 from the
dozen scratch checkouts under `.git-exclude/tmp/` — and **448/449 has been recorded as a project
figure in release records for many milestones.** `unsafe-audit` read **299** in every tree, which is
what made the asymmetry visible.

**The verdict was never wrong, and that distinction matters.** Those scratch copies are copies of an
annotated tree, so `missing annotation` stayed `0` and no safety claim ever rested on the count. What
was wrong is that the count was not a property of this project: it varied with whatever happened to
be on the machine. A gate reporting a number that looks like coverage and is mostly noise is the
**E-014** class, in the release evidence.

**The fix already existed in the tree, one directory away.** The walk skipped three literal names —
`target`, `.git`, `fjell-mmio-audit` — and `.git-exclude` is none of them. `fjell-unsafe-audit` had
**exactly this defect**, it was fixed, and its doc comment says so in terms: *"a scratch checkout
under `.git-exclude/tmp/` doubled this tool's own count before this fix, because `.git-exclude` was
not one of the three literal names the old walk skipped … the boundary still must not be a
hand-maintained name list (E-015's family; that was E-025)"*. **The sibling never received it.**

`mmio-audit` now derives its scope the same way — `git ls-files --cached --others
--exclude-standard`. One enumerated name remains and it is **not** scope: the tool's own directory,
because its `MMIO_PATTERNS` constants would otherwise read as access sites. That is self-exclusion,
which is what the original comment meant.

**Two checks, because a narrowing fix must be shown not to have narrowed too far:**

* the working tree now reports **41 sites, 0 missing, 0 invalid**, matching the pristine clone
  exactly;
* the **control** — an uncommitted, unannotated MMIO site dropped into `crates/fjell-cap/src/` —
  is **still caught** (42 sites, `missing annotation: 1`). Uncommitted work is exactly when an audit
  should speak up (RFC-0.28-005 §6), so a fix that quietly audited only tracked files would have
  been worse than the defect.

**The test that should have caught it asserted nothing.** The only test touching the old walk called
it and then wrote `let _ = records.len();`, tolerating zero records, with a comment excusing the
case. It is replaced by one that builds a **real git repository** and proves all three cases:
a committed file is audited, an untracked file `.gitignore` does not exclude is **still** audited,
and a file under an ignored directory is not. A fake world cannot show that `.gitignore` is honoured.

**For the owner, and not taken here:** the historical records' 448/449 figures are wrong by the same
mechanism. Whether that takes an erratum is the owner's call; this record states the measurement and
leaves the filing.

## What shipped

### RFC-0.45-002 — capability installation runs, narrowly (closes **E-123**, narrows **E-011**)

`sys_cap_install` (`CapInstall`, 17) is dispatched. `syscall-surface`: **36 declared / 33 dispatched
/ 3 undispatched** (`TaskKill`, `MmioUnmap`, `DmaShare`).

**The design decision that carries it is a deletion.** RFC 056 specified a `target_task_id`; the
shipped primitive has **no target argument**. The capability is installed into the caller of the
installer's pending IPC reply edge, read with `CapTable::peek_reply`, which takes `&self` — **the
compiler, not a convention, is what stops it consuming the edge**. A stale or forged target is
*unrepresentable* rather than rejected, and a compromised broker can write only into a task that is
blocked in a call to it. That is stronger than the validation RFC 056 asked for.

The decision is `fjell_cap::install::check_install`, a **pure function** that owns the order and the
error of every refusal, so each is demonstrable on the host and shown red by its own mutation. The
kernel keeps only the first check, which needs the CSpace and the lease table. Six bounds:
**kind** (`Endpoint` only), **rights** (non-empty, inside the installer's envelope masked so
`CAP_INSTALL` can never be conferred), **target** (no argument), **lease** (non-zero, owned by the
installer, `Active`), **object ≠ 0**, and **object allocated**. `BROKER-004` — cited by the broker
and **defined nowhere in the tree** until now — is written down and satisfied: the broker creates a
lease per grant, the kernel binds the capability to it, the real lease id reaches the
`DelegationRecord`, and revoking it kills the capability.

Also: the fail-open `_ => CapKind::Endpoint` arm is gone (an unmapped class is refused by name);
`init`'s slot-27 `CapInstall`, whose comment promised a revocation that never happened, is
**removed**; `sys_cap_install_with_rights` is **deleted** (E-011's discarded parameter); and
`CAP_REVOKE` is honoured only for a lease the broker granted, at the request of that grant's grantee
or `init`, through a host-tested predicate.

**Audited under its own names:** `CapInstalled` `0x0601` and `CapInstallRejected` `0x0602` — the
codes `RFC-v0.7.4-003` specified — decoded as `cap.installed` and `cap.install_rejected`, with the
object in `arg1`. The `audit` tier requires both, **including which object was installed**.

### RFC-0.45-003 — an `Implemented` RFC shows that its mechanism runs

`rfc-evidence`, the **23rd** subcheck. An RFC from 0.45 on may not be `Implemented` without an
`**Evidence:**` line in its header block whose citations **resolve**: `syscall:` (declared **and not
undispatched**), `marker:` (a line of a profile's committed `expected-markers.txt`), `file:` (a
non-empty file inside the repository), `test:` (a named `#[test]`). `cargo xtask rfc promote` refuses
the move to `done/` by calling **the gate's own `examine`**, not a second parser — ruling 13's
condition, and the same constraint moved `syscall-surface`'s two parsers into a shared
`syscall_table.rs` so `rfc-evidence` resolves `syscall:` through them.

**Its PASS line states its own limits in words**, which is the part that matters for an instrument
built to catch instruments that overclaim: the 227 pre-0.45 RFCs it does not cover, that it enforces
nothing yet *(it does now — see the clean-clone check)*, its count broken down by kind with `test:`
named as the weakest, and the two known-false statuses **by name**.

`KNOWN_FALSE` and `WAIVERS` are two lists, on the ground of **provenance**: a waiver is an
implementer's judgement inside the gate; a known-false status is the owner's pending lifecycle
decision. Neither touches a status line.

### RFC-0.45-001 — the test environment presents a NIC (narrows **E-122**, follows through on **E-118**)

Two profiles. **`net`** attaches `-netdev user,id=n0,restrict=on -device virtio-net-device,netdev=n0`;
**`net-absent`** attaches none. Each profile's committed `qemu-command.txt` is the evidence, and it
holds: `net` shows the device, `net-absent` has **zero** occurrences of either flag.

The driver scans the eight transports through one `MmioRegion` capability — region 3, slot 34,
**`MMIO_MAP` only**: no `INSPECT`, no IRQ, no DMA, no endpoint — reads `MagicValue` and `DeviceID`,
and prints **one of three** lines: *found* (measured at transport slot 6 under QEMU 11.1.3; the
profile pins the magic and the id, not the slot, because the slot is QEMU's), *no device found after
all eight were read*, or *cannot scan*. **"No device" and "could not look" are different answers** —
**E-118** from the other side — and since the follow-ups the rule is a **pure host-tested
predicate** (`scan.rs`), so breaking it goes red on the host without needing a boot that can
withhold a grant.

A new profile key **`expect_absent`** asserts no console line contains a given text, and the loader
refuses two unusable shapes: an absent text contained in one of the profile's own required markers,
and `expect_absent` with no required marker at all — a run that never booted would otherwise
satisfy it.

**The over-grant is named, not hidden:** region 3 covers all eight transports and the mapping is
read-write, because the kernel cannot enforce "reads only" on an MMIO window. RFC-0.43-003 ruled
that pre-existing question, and this line inherits it rather than pretending otherwise.

## Known limitations at this release

The register stands at **123 entries, 9 accepted, 0 open**, and every accepted erratum is referenced
in `v1-limitations.md` (`errata-limitations` PASS). The ones this release's reader should know:

* **The lease table is never recycled** (**E-110**, limitations row): a revoked lease keeps its slot
  for the life of the boot, there are 32, and **0.45 makes the limit reachable from a production path
  for the first time** — the broker creates one lease per grant *request*. Measured by the dev team:
  a requester looping request-then-drop is granted **26 times**, after which **every other task's**
  `sys_lease_create` fails. **Deferred to 0.46 deliberately**, not overlooked: making a slot reusable
  means bumping a generation the epoch model's safety argument (`LEASE-001`, `LEASE-VERUS-005`,
  retire-before-wrap) does not currently use, which is a formal-verification surface and not
  cut-week work.
* **`sys_lease_revoke` checks no ownership** and every `LeaseAdmin` has scope `Any`. The broker now
  holds one, so the only bound on it revoking any lease in the system is the broker's own
  `CAP_REVOKE` authorisation check. Before 0.45 it held none.
* **Runtime installation does not bound *which* allocated endpoint it may name** (row 26). The
  kernel bounds six things; the seventh — which of the 32 endpoint objects — is the broker's policy
  table's choice, because the installer **fabricates** a capability from an integer rather than
  *deriving* one it holds. The `audit` tier asserts which object was installed, demonstrated on a
  real boot by asking for object 22 (`configd`'s endpoint) and watching `policy` stay green while
  `audit` went red. **That is coverage, not a bound**; the bound is the 0.46 property.
* **There is still no working network** (row 25, **E-122** narrowed): nothing sends or receives a
  packet, `sys_net_recv` exists nowhere, `netd` exits before its event loop, `secure-transportd`'s
  release handshake returns `Err` unconditionally, and the virtqueue logic in the driver's library is
  **not linked into the image** — 0.45 links one module from that crate, the scan predicate.
* **Two RFCs still say `Implemented` where the work has not shipped** — `RFC-v0.7.3-001` and
  `RFC-v0.7.3-002`. `rfc-evidence` names them on every run. Their disposition is blocked on a
  lifecycle question **RFC 000 cannot answer**: it defines neither `Implemented-with-Errata`, carried
  by **12** RFCs and accepted by the status reader, nor `Closed`.
* **RFC 056's status became true on 2026-11-18** and was false every day before it. It carries a
  dated annotation naming the three ways the shipped design differs from its text — no target
  argument, an installer-owned lease, `Endpoint` only — rather than being edited to match.

**No accepted-risk statement is written for this release.** No gate that should have blocked was
left unpassed: Gate 1's red was fixed and re-run, not accepted.

### The pre-publish re-read found a stale claim, and it changed what gets published

The cycle requires re-reading `crates/fjell-os/README.md` before publishing, because it carries
counts and is the copy outsiders see first. **It said "a 33-tier test suite"; 0.45-001 added `net`
and `net-absent`, so it is 35**, and the release run reports 35. Corrected on `main` at **`29dccdf`**,
*after* the tag — the tag is **not** moved or deleted.

**So the crates are published from `main`, not from a worktree at the tag**, which departs from
0.44.0's recorded practice and is a deliberate decision by the architect under the owner's stated
philosophy:

* **crates.io renders a version's README permanently.** A version can be yanked but never deleted,
  and the page re-fetches its images forever. Publishing a knowingly false count to the surface
  outsiders read first is the defect the owner's second clause — *APIs and UI/UX must not let users
  be confused or misunderstand* — forbids, and it is the one defect in this cut that **could not be
  corrected afterwards**.
* **0.44.0's "from the worktree at the tag" governs a different case.** There, `main` carried
  *unrelated* post-record work that had no business in a publish, and the record said so in its own
  section. Here the whole difference is the single line that makes the published page true.
* **The divergence, bounded and stated:** `git diff --name-only 0.45.0 main` is
  **`crates/fjell-os/README.md` alone**, `1+/1-`, the digits `33` → `35`. Nothing else.

**The rule this sets, narrowly, so it is not a loophole:** only a correction produced by the
mandated pre-publish re-read may ship ahead of the tag; it must be documentation-only; and the
record must carry its exact diff and its reason. Anything wider waits for the next version.

**This was also a miss in exit criterion 8.** That criterion found three real falsehoods in
`services.md` and `v1-limitations.md` and did not sweep this file's tier count — the one file the
procedure names by path. Nothing gates a tier count in prose, which is why it drifted: the same shape
as **E-116**'s README version line, and a candidate for the same treatment.
