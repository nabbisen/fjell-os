## What shipped

### RFC-0.44-001 — the attestation can be asked for, and the export nobody wants goes

Closes **E-121**, **E-120**, **E-087**.

`attestd` built a record on every boot that **no image could ask it for**, while
`fjell-diag-format`'s bundle carried `last_attestation_available` documented *"permanently
`false` today"* **precisely because nothing queried**. `diagnosticsd` now holds `CAP_ATTESTD_EP`
— slot 5, **`CALL` only** — and sends `LATEST_DIGEST`, answered with a 32-byte
`LATEST_DIGEST_REPLY` or `NO_RECORD`. `attestd`'s state became a single `Option<Digest32>`
(`crates/services/fjell-attestd/src/main.rs:374`), which makes **E-076's zero digest
unrepresentable** rather than guarded against — the change the review singled out.

The two chunked exports that replied success having transferred nothing were **deleted rather
than implemented**: `0x307`–`0x309` and `0x316`–`0x318` are **retired, not reassigned**. The
ground is that the consumer wants **32 bytes**, which one reply carries in four words — *not*
that nothing called them. A `sys_ipc_reply4` wrapper was added, which **removed** a
callsite-audit allowlist entry rather than adding one.

**And "available" is not "attested".** A real boot reports `measurement=1` with every other
availability bit `0` (**E-095**), signed by the development trust provider with a zero dev key,
**which authenticates nothing**. So a bundle can now report an available attestation whose claims
are nearly all placeholders. The field's own documentation says so.

### Small item A — the threat-model gate (closes E-027)

Two documents asserted a *"threat-model gate"*; **neither the gate nor the name one of them used
existed.** The new subcheck derives the threat population, requires each entry to cite a
*resolving* RFC in `rfcs/done/`, and cross-checks `standards-mapping.md`'s count. **Its first run
found `T23` citing none, with its own `Defence` line reading `None.`**

It is waived **by name**, only while that line says so, printed on every run. The gate was not
committed red and the threat model was not quietly edited to suit it.

**E-027's defect lived in two documents, not one.** The live threat model made the same claim by a
specific name — `ci-threat-model-check`, a CI job that does not exist; what was built is a
`consistency-check` subcheck named `threat-model`. Corrected, with the finding added to E-027's
closure. That is the same one-document scoping as E-117, E-119 and E-121.

### Small item B — two pointers at documents that do not exist (closes E-028)

Closed by correcting the **pointers** — including one inside a `compile_error!` a developer meets
on a misconfigured build — **not** by writing the documents. RFC-v0.7.3-002's two crypto
documents still do not exist; commissioning them is the owner's.

### Small item C — the Clock gate's rights check is demonstrated

0.43's case proved refusal for *no authority* and *wrong kind* but **not that the right is what is
checked**: weakening the required right to `NONE` left it passing. `neg-test` now holds a
`Clock`-kind capability at slot 15 with `CapRights::NONE`, on slot 9's deliberately rights-less
`Interrupt` precedent. The three outcomes are **distinct by construction** — empty slot gives
`InvalidCap`, another kind gives `WrongType`, the right present would *succeed* — so
`PermissionDenied` can only be the rights check refusing. **Shown red seven ways**, including the
mutation the previous version passed and slot 15's grant removed, which proves the new capability
is load-bearing rather than decorative. No new marker was added; the existing one now fires only
if all three refusals are exactly right.

### Small item D — `doc-counts`' rule stops being implemented twice

`rfc promote`'s pre-flight now calls `fjell_consistency_check::readme_counts::disagreements`.
`doc-counts`' output is byte-identical before and after on five cases.

### Small item E — the bundle's attestation digest is compared

The `remote-diag` tier now judges the digest the bundle carries against `attestd`'s own, so
statement 1's new path has a comparer rather than a claim. The judge's first message described the
symptom rather than the cause; the real-boot red showed it and it was fixed before review.

### RFC-0.44-002 — withdrawn before it was written

It would have given `fjell-net-format`'s two layouts a schema. **Neither type has any consumer** —
`netd` imports neither, the unlinked driver library imports neither, and one is not even
re-exported. A schema would have been *"a file asserting coverage of bytes nobody writes"*, which
is the class **E-073** itself refuses. Its net half stays ACCEPTED.

## Exit criterion 8 — what it found

**One finding, and it is about the gate document rather than this release.**

`docs/src/releasing/v1-readiness.md` is the v1.0 readiness matrix. **The word *mitigate* appears
nowhere in it.** No row requires a defence for every in-scope threat — `Threat model finalized |
RFC-v0.15-002 | DONE (v0.15.0)` is a claim about the *document*, and a model is finalized when its
enumeration is settled. So **T23's missing defence touches no cell**, and v1.0 is not, as written,
blocked by it. Making that a requirement would need a **new row**, not a status change.

**That is the owner's decision and it is left open here rather than taken.** It is recorded
because a gate document that quietly does not require what its readers assume is the **E-014**
class, and the response to that class is to say so.

**Two rows were re-read rather than assumed**, being the only ones 0.44 could have moved:

* *Attestation profile v2* says the record's uncomputable digests *"are written as zero behind an
  availability byte the encoder zeroes"* and that `attestd` holds a `CALL`-only capability to
  `measuredd`. 0.44 adds a **second `CALL` edge in the same direction** (`diagnosticsd` →
  `attestd`) and changes `attestd`'s *last verified record's* digest to an `Option<Digest32>` —
  **not one of the record's claim fields**, so neither clause moves.
* *Threat model finalized* stands, for the reason above.

`readiness-check`: **DONE 56 / IN PROGRESS 2 / DEFERRED 3 / OPEN 0**, exit 0 — unchanged by
0.44.0. The 0.44.0 clause was appended to the document rather than overwriting 0.43.0's.

**`readiness-summary` was not seen red at this cut**, because the heading moved in the version-bump
commit; the evidence that the subcheck works is instead that `release-rehearsal` read it green with
heading and workspace version both at 0.44.0. 0.42.0's record carries the red-firing transcript.

## The architect's own findings this cut

1. **E-121's central claim was mine and it was false.** I wrote that `attestd` *"cannot be asked
   for anything"* having enumerated `spawn.rs` alone; `main.rs` installs slot 4 → `object_id: 3`,
   `CapRights::CALL` into `init`'s CSpace, and every boot prints `record generated (v2)`.
   `capability-topology`'s own doc says `init` is spawned from `main.rs`. Recorded in the erratum.
2. **"All 23 threats cite an RFC" was mine and it was false.** The script I reasoned from ran its
   last section to end-of-file and swallowed the *Operator obligations* citations that follow.
   The dev team pinned it with `the_last_section_does_not_inherit_the_citations_that_follow_it`.
3. **I recommended deleting `attestd`'s surface, and that was the wrong ruling.** It reasoned from
   *nothing calls it*, which cannot distinguish unwanted from unfinished. The owner asked whether
   introducing the missing caller was not the reasonable move, and `fjell-diag-format` turned out
   to carry a field documented as permanently false **because** nothing queried. The reversal is
   in the register, the RFC README row and the changelog, not only here.
4. **I repeated the 0.42.0 concurrency mistake.** I ran `cargo xtask consistency-check` three
   times while the criteria 4–6 chain was in flight. **Criteria 5 and 6 were re-run alone**, and
   this record cites only those runs — `tests/runs/20261115-093709` and the clean
   `release-rehearsal`. Criterion 4 is taken from tiers 1–6 of the same clean run for the same
   reason.
5. **An absence probe of mine was run against a corpus that could not contain the line.** While
   re-reading `v1-limitations.md` for criterion 8, I searched `tests/runs/` for
   `secure-transportd: handshake failed`, found **zero** hits, and concluded for a moment that
   **E-122's own wording was wrong**. It is not: `tests/runs/` holds tier logs, which do not
   retain serial output — serial lives in `tests/qemu/artifacts/<profile>/serial.log`. A fresh
   `svc` boot at this tip prints `secure-transportd: starting`, `ready`, and
   **`handshake failed`**, in that order. The probe was the error, not the erratum.
6. **The passage that prompted item 5 is accurate, and was checked rather than corrected.**
   `v1-limitations.md` says `secure-transportd` *"now genuinely exchanges messages rather than
   busy-spinning on an empty slot"*. The same boot shows `upgraded: update index fetch returned no
   index` immediately after the failed handshake — so the exchange happens and the failure is a
   **reply, not a hang**. The handshake failure is row 25's disclosure, on a different axis. No
   edit was made.
