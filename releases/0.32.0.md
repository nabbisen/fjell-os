## What shipped

### RFC-0.32-001 — a fuzz harness that fuzzes

Five of the harness's eight targets called functions that did not exist, so it
had never compiled, and the scheduled job described as fuzzing weekly had failed
on every run for three months (**E-043**). It now has one target per real byte
decoder a host crate can reach — **seven** at this release — seeds replayed on
every event, a 300-second run per target on schedule and dispatch, a matrix
derived from `cargo fuzz list`, and a crashing input uploaded rather than
discarded.

Its first real run found `fjell-dtb-derive` adding two offsets read from the
device tree without checking the sum — a crafted tree panicked it in 30 seconds
(**E-047**, fixed). Closes **E-043** and **E-047**.

### RFC-0.32-002 — bytes from another service are not a struct

`semantic-stream` and `proxy-text` rebuilt a message by reinterpreting another
service's bytes as a Rust type containing enums. Miri named the undefined
behaviour at `.correlation_id.<enum-tag>` — and a **zero-filled** buffer, what a
receiver holds before its first message, was not undefined behaviour at all but
decoded silently into a fabricated envelope.

A versioned wire format decoded by safe code returning `Result`; framing
enforced against the length `BEGIN` declares; `semantic-stream` re-encodes what
it forwards; checksums over named fields rather than struct memory. An envelope
is 143 bytes in 7 IPC calls, where it was 4,936 in 157. The six raw
reinterpretation sites E-046 found outside the kernel are gone — **0 at this
tip, re-probed; the kernel's 4 remain, out of scope**. Closes **E-046**.

### RFC-0.32-003 — documentation that can be found

75 of the book's 134 pages, all 41 ADRs among them, were in no navigation; stubs
pointed at documents outside the book; four directory names existed twice; and
nothing published it. Every page — **173** at this release — is reachable from
`SUMMARY.md`; one prose root; records to `releases/`; the RFC corpus to `rfcs/`;
mdBook pinned at 0.5.4 and checked against CI; the book deployed to GitHub Pages
from `main`, at <https://nabbisen.github.io/fjell-os/>. Five subchecks hold it.
Closes **E-050**.

### RFC-0.32-004 — advisories that exist

One process document, one intake channel, a register **empty and checked while
empty**, and published advisories against every `Cargo.lock` checked in CI. The
check's first run was red — RUSTSEC-2026-0204 (`crossbeam-epoch`) and
RUSTSEC-2026-0190 (`anyhow`), neither reaching a published crate, the kernel or a
service — and both were fixed by patch-level updates (**E-053**).

**Owner decisions recorded this release:** acknowledgement within **7 days**, a
severity decision within **14 days**, every time a target rather than a
guarantee; and a defect found internally gets an advisory **only when it
reaches a published crate** — E-046 receives none. Closes **E-051** and
**E-053**.

## The implementer's own findings this cut, recorded

Three procedures ran at a real cut for the first time. Two of them found
something about themselves, which is the argument for running them rather than
assuming them.

1. **Criterion 9's dispatch cancels the push run's `pages` job.** The push run's
   first attempt concluded **`cancelled`**: its `pages` job was cancelled 81
   seconds in by the dispatch run's `pages` job. RFC-0.32-003 D18 gave `pages` a
   `concurrency: { group: pages, cancel-in-progress: true }` so two pushes cannot
   race onto the site — and a `workflow_dispatch` on `main` deploys too. So
   **dispatching against the release commit, as criterion 9 requires, cancels
   the push run's deploy by construction, at every cut.** It is harmless in
   substance — the dispatch deploys the same commit — but it leaves the run
   criterion 9 reads reporting `cancelled`.

   Repaired without touching the release commit: after the dispatch run
   completed, **only the cancelled job was re-run** (`gh run rerun 35089262713
   --job 104771565361`), against the same commit, with nothing left to collide
   with. Attempt 2 is green. **`ci.yml` was not changed at the cut**: that would
   have changed the release commit. Two fixes, for whoever owns it: skip `pages`
   on `workflow_dispatch`, or set `cancel-in-progress: false` so a later deploy
   queues behind an earlier one instead of cancelling it.

2. **`gh run view --json jobs` reports a failed not-gated tier as `success`.**
   `qemu-negative (store, false)` and `(upgrade, false)` fail with exit code 1 in
   both runs — ``profile `store` FAIL``, ``profile `upgrade` FAIL`` — and
   their job *and* step conclusions read `success`, because the step carries
   `continue-on-error` for not-gated tiers. GitHub's jobs API exposes a step's
   `conclusion`, not its `outcome`, so **criterion 9's written method cannot
   tell these two failures from passes**; only their logs can. The 0.31.0
   record listed both under success. They are expected to fail, for a recorded
   reason — this is not a regression — but a record reading "37 success" should
   say that two of the 37 are failures the job table cannot show.

3. **The cut handoff's version table named one crates.io logo URL; there are
   three.** It listed `crates/fjell-os/README.md:2`; the standing handoff §3
   names that and `crates/fjell-os/src/lib.rs:5` and `:6`. Following the table
   alone would have left `html_logo_url` and `html_favicon_url` pinned to
   `0.31.0`. All three were moved.

4. **The register holds 12 ACCEPTED errata, not 11.** 53 entries = 41 CLOSED +
   **12** ACCEPTED + 0 OPEN. The cut handoff's list omits **E-004**, whose
   status cell reads `ACCEPTED (v1.0 limitation)` — the same parenthetical my own
   first count stumbled on. `errata-tracking` agrees: 53 entries.

5. **Two figures moved after the handoff was written, and the tree was used.**
   Seven fuzz targets, not six (RFC-0.32-002 added the wire decoder), and 173
   book pages, not 171 (RFC-0.32-004 added two).

6. **The standing handoff's order puts the record before the steps it records.**
   Step 11 writes the record; steps 13 and 15 produce what §4.10 and §4.12 put in
   it; and step 13's dispatch must be *of the release commit*, which requires
   the cut commits to be pushed first. So the record was written after reading
   both runs — push, dispatch, read, then record — which is the only order that
   works. Worth writing down.

7. **The standing handoff §4 calls `releases/0.29.0.md` "the most recent".**
   0.30.0 and 0.31.0 have been cut since. Every path in the handoff resolves at
   its new location; that sentence is the one stale thing in it.

8. **Two errors of mine during this cut, both caught before they reached a
   commit.** The first comparison of committed prebuilts against the baseline
   reported *"29 of 29 differ"*: `cut` and `stat` were not found in the shell it
   ran in, so every computed digest was empty and compared unequal. Re-run under
   bash with a control that a digest was actually computed: 4 of 29. And the
   first attribution table labelled all four code binaries "code and the bump";
   checking their digests either side of the rebuild showed three of them
   untouched by the bump.

9. **The baseline was moved aside, not `rm`'d.** The procedure says `rm
   tests/repro/baseline-digests.txt`; the tool only needs the file absent, and
   a copy kept outside the tree cost nothing. The re-recorded file was verified
   against it.
