## What this release is

Six RFCs and **six errata closed** (**E-101**, **E-102**, **E-103**, **E-104**, **E-107**, **E-109**); two filed and carried to 0.42 (**E-105**, **E-106**, both ACCEPTED); one filed and withdrawn the same day (**E-108**). `auditd` drained the
kernel's audit ring once at start-up and then waited on a message nothing sent, so the trail stopped at boot. It now parks on the ring (`sys_audit_wait`), wakes on the append, drains until empty, and prints a
`{"gap":…}` notice where records were lost. The attestation record's remaining placeholders are disclosed behind five availability bytes (`SCHEMA_VERSION` 3 → 4). A failed `reserve_range` changes nothing. A 21st
consistency subcheck fails prose that still asserts a closed erratum. An intermittent boot failure and an intermittent build difference — each of which blocked this cut — were given causes; one is a property of
the host and is **disclosed, not fixed**.

**There is no security advisory.** Five statements the cut handoff requires, as the CHANGELOG makes them:

1. **The trail records less by default**: `task.switch` is no longer appended at all (`RECORD_TASK_SWITCH = false`), applied at the append site, because the ring drops the newest record when full.
2. **The trail is lossy and says so.** A normal boot of the `audit` profile printed **905** records and reported **1,447** dropped (retained run `tests/qemu/artifacts/audit/runs/20261104-004647`).
3. **The attestation record is schema 4, and a version-3 verifier cannot read it**: `schema_version` is inside the signed canonical stream, so a v3 verifier gets a digest mismatch and a failed signature, not a silent misparse.
4. **No service can express a duration** (**E-106**). `storaged` waits for the disk by counting 500,000 `sys_yield` rounds; its failure report no longer calls that a timeout.
5. **The release profile is part of the reproducibility claim** (**E-107**).

**What still does not hold, in the same breath:** a healthy disk that is merely slow fails the boot at M6 (**E-104**, closed on a **cause**, not a fix — limitations row 19); the store is written to the wrong sector
(**E-105**, row 17, latent); three of the measurement chain's four events are placeholders and the kernel's own image is unmeasured (**E-095**); and the record is signed by the development provider, not a
hardware root.

## What shipped

### RFC-0.41-001 and RFC-0.41-002 — the audit trail reaches someone, and no service receives on the shared endpoint (close E-102)

`sys_audit_wait` (syscall 61) blocks the caller until the ring is non-empty, under the `AuditDrain` capability; the lost wakeup is closed by a level, not a latch; `a1` reports whether the call parked, and the `audit` tier
requires the guard's own path to have run during its sweep. `auditd` drains until empty and prints `{"gap":…}` where records were lost. Three images that received on endpoint object 0 (`configd`, `neg-test`, `netd`) got
dedicated objects; `init` is no longer granted slot 0; `capability-topology` fails any install giving a receive right on object 0. The record line's final shape, once:
`{"seq":N,"kind":"…","arg0":N,"arg1":N,"result":N,"task":T,"tick":K}`, `task` rendering `null` for "not task-scoped", `tick` a **count of traps, not wall time** (the timer interrupt is never armed). `task.switch` is no longer recorded.

### RFC-0.41-003 — the attestation record's placeholders stop reading as state (closes E-101)

`SCHEMA_VERSION` 3 → 4; five availability bytes (keyring epochs; snapshot id with its reason, named `snapshot.id_and_reason_available`; health status; last-advance source; freshness key epoch), each before the claim it
qualifies, the claim zeroed by the encoder when its flag is 0; the counter value is zeroed by the encoder as well. Proven rather than assumed: removing the five bytes and rewinding the version word recovers the v3 golden exactly.

### RFC-0.41-004 — frame reservation is all-or-nothing (closes E-103)

`reserve_range` validates the whole range before changing anything; a failed call leaves used bits, owner map, `free_count` and hint bit-for-bit untouched. Host-lib tests 763 → 768, ignored 1 → 0.

### RFC-0.41-005 — a gate catches prose that still asserts a closed erratum

`closed-erratum-prose`, the 21st subcheck; two rules (a live status word nearest a closed id; a present-tense appositive claim), each shown failing on the real file it would have caught; 725 references to 96 closed errata, none asserted as live.

### RFC-0.41-006 and its follow-on lines — the intermittent boot fault gets a cause (closes E-104), and two clean builds stop disagreeing (closes E-107)

The `M6: block I/O error` is a host write that does not complete inside `storaged`'s 500,000-round poll budget with the device healthy; two natural captures spanned **1,004,789** and **1,004,892** traps. **Not fixed, disclosed
(row 19).** The failure report is `storaged: io incomplete after 500000 poll rounds …` over two console lines (83 and 133 characters, under the console's 160-character split). `cargo xtask boot-loop` boots to the M6 decision many
times; it reproduced the signature on a deliberately slow disk and **has not reproduced the natural rate**. `repro-check` keeps both builds' artefacts on a mismatch. E-107: `codegen-units = 1` is pinned in `[profile.release]`
with a comment saying why — 11 of 150 unpinned builds produced a second kernel, 0 of 150 pinned; 20 of 34 artefacts moved; the kernel is 336,288 bytes (3,912 smaller); the cost is **not a measured number** — only the
interleaved soak's 2.9 s → 3.4 s (about +17%) is like-for-like.

### E-109 — the setup document called the release-blocking prover optional

`local-development.md` called Verus optional and its recipe pinned a retired version; **it caused this cut's second missing-tool pause.** The recipe is now cited from `verification/verus/TOOLCHAIN.md` and not copied.

## What this release does not claim

- **That E-104 is fixed.** Its cause is known and its behaviour is unchanged: on a slow host a boot may fail at M6 (row 19). The budget is a count of rounds, measured in traps, and no duration is claimed anywhere.
- **That the store is written correctly.** Every write lands at sector 0 with part of each chunk lost, while `init` prints `block write ok` (**E-105**, row 17; latent — nothing reads the store back).
- **That `tick` is a clock.** It counts traps. **That the trail is complete** — a record count is not an event count in a lossy trail.
- **That attestation is real.** The record is truthful, not complete: the kernel's own image is unmeasured, release / rootfs / policy verification does not exist (**E-095**), and the signature is the development provider's keyed SHA-256 digest.
- **That the harness `boot-loop` measures the natural rate.** It does not reproduce it, so a clean count from it is not evidence.
- **That a clean dependency check describes what Fjell OS ships.** The published crates have no third-party dependencies; the check covers tools, tests and the development-grade crypto crate, and says so itself.
- **That CI gates the release.** Criteria 9 and 11 *record* CI; every gate runs locally.
- **Cross-machine reproducibility.** The claim is for this toolchain and the committed `[profile.release]`, on one machine.
- **That the emulator is captured by tooling.** QEMU 11.1.3 is stated here by hand (row 20).

### The publishes

Applied after the tag, so that the three logo URLs pinned to `/0.41.0/` resolve — crates.io renders a
version's README forever but re-fetches the images every time. All three were checked at their named
locations before publishing (`crates/fjell-os/README.md:2`, `src/lib.rs:5`, `src/lib.rs:6`), and the
three assets they name are present and tracked.

`fjell-abi` then `fjell-os`, in that order, because `cargo publish -p fjell-os` cannot resolve until
`fjell-abi` is on the index — its dry run failed with
`failed to select a version for the requirement fjell-abi = "^0.41.0"`, which is the order being
enforced rather than a defect. `cargo publish` reported each as `Published … at registry
crates-io` after waiting for the index.
