# RFC-0.34-003: What the instruments cannot see

**Status:** Proposed
**Milestone:** 0.34
**Tracks.** **E-065**'s first survivor — `fjell-semantic-format::wire`, the IPC codec
every publisher and presentation exchanges, which has no generated description — and
**E-067**, the ABI baseline's blindness to a braced struct's fields and a trait's
items. One line because both are the same question asked of two instruments: **what
does this check actually cover, and how would anyone know?**
**Touches** *(indicative)*: `crates/formats/fjell-semantic-format/`,
`crates/fjell-canon/`, `crates/fjell-schema/`, `tools/fjell-abi-snapshot/`,
`tests/abi/snapshot.json`, `docs/src/releasing/v1-limitations.md`.
**Relates to:** RFC-0.33-003 (the method: the encoder is the description, goldens
captured from the unmodified encoder first); RFC-0.33-004 D5 and its §C (the enum
hash, and the discipline for reading what a re-record reveals); RFC-0.32-002 (the
wire codec's own line, which made the envelope's bytes a boundary).

## Summary

Re-derived 2026-09-25 at `728d79c`.

### Finding 1 — the format on the live boundary is the one with no description (E-065)

RFC-0.33-003 gave nine formats a description **generated from the encoder that
writes them**, compared in Gate 1, with a note in each file of what it used to
claim. Five produce bytes and have none. Four of the five are reachable by nothing
outside their crate, or are `#[repr(C)]` layouts the kernel writes raw. The fifth is
**`fjell-semantic-format::wire`** — 981 lines, `MAX_WIRE_BYTES` 4,624, and
`crates/formats/fjell-semantic-format/schema/` does not exist. It is the format
services exchange across a trust boundary: every `SemanticEnvelope` a publisher
sends and every presentation renders, including the two RFC-0.34-001 shipped.

### Finding 2 — thirty-three structs and one trait are hashed by their first line (E-067)

`tests/abi/snapshot.json` holds **443 items**: 262 `const`, 126 `fn`, **33
`struct`**, **19 `enum`**, 1 `trait`, 1 `type`, across eight crates. Since
RFC-0.33-004 D5 the enums' hashes cover their variants. A braced struct's hash is
still `pub struct AuditRecordBin {` and a trait's items are not descended into, so
**adding a field or a method is zero drift** — asserted today by the snapshot's own
test `a_braced_structs_fields_are_still_outside_its_hash`, which this line must
invert. Among the scanned crates are `fjell-abi`, `fjell-cap`, `fjell-service-api`
and `fjell-audit-format`, whose `#[repr(C)]` records the kernel writes raw.

## The settled part

**D1 — the wire codec writes through `Canon`, against goldens captured first.**
RFC-0.33-003's method exactly, unchanged: the encoder is the description; goldens
are captured from the **unmodified** codec before any rewrite and must be reproduced
byte for byte; the `.frozen` file is generated by the same function that writes the
bytes, and compared in Gate 1.

**D2 — no second list of fields.** If the codec's shape cannot be expressed by
`Canon` as it stands, `Canon` gains what it needs and the gap is named — as
`fjell-bundle-format`'s big-endian gap already is. A hand-written description is
E-045 again.

**D3 — the ABI hash covers a braced struct's fields and a trait's items**, with the
same normalisation the enum hash uses, and the baseline is re-recorded **once**.

**D4 — the drift the re-record reveals is read and named, not absorbed** — §C of
RFC-0.33-004, applied: a field or method **removed** from a pre-existing item that
nobody noticed is escalated here, not written into a commit message and forgotten.
That line's own history (every tag from `0.10.0`, consecutive lists diffed, one
deliberate removal in twenty-two releases) is the standard.

**D5 — demonstrated failing, each:** a wire field renamed or re-widthed turns the
comparison red and names it; a hand-edited `.frozen` file does too; a field added to
a scanned struct, and a method added to the trait, each give `Changed sig: 1`
naming the item; and the inverted test replaces the one that asserts blindness.

**D6 — E-065's other four survivors are not touched here**, and stay named.

## The open questions

**§A — what describes a decoder?** The frozen file describes the **encoder**. The
wire codec also decodes, and a decoder that reads different fields than the encoder
writes is precisely the class E-045 hid. **Lean: a round-trip per sample *and* a
statement of what the description does not cover on the decode side** — say which,
rather than implying the file covers both.

**§B — can `Canon` express this codec at all?** Chunked frames, a length-prefixed
token stream and a sentinel are not the flat field lists the nine converted formats
had. **Lean: extend `Canon` with what the codec needs** (counted groups already
exist; say what is missing) — and if some part cannot be expressed, the honest
output is a description that stops where `Canon` stops, plus a named survivor. Do
not invent a second notation.

**§C — does hashing a struct's body make Gate 4 noisy?** Private fields, doc
comments, `#[repr(C)]`, `#[derive(...)]`, field order. **Lean: normalise comments
and whitespace as the enum hash does; include attributes that are part of the ABI —
`#[repr(C)]` certainly is — and say for each of the others whether it is in or out,
in the tool's own doc.** A hash that changes on a rustfmt reflow will be
regenerated without reading, which is D4's failure mode.

**§D — order.** **Lean: E-067 first.** It is mechanical, and once it is in place the
codec line's own ABI additions are visible to Gate 4 by body rather than by
declaration — the instrument checks the work that follows it.

**§E — how far does the description go for a format with a version?** The semantic
envelope carries a schema version and RFC-0.32-002 fixed its decode precedence.
**Lean: the description carries the version field like any other**, and the file's
header states the wire version the way the disk structures' headers now state their
on-disk version (RFC-0.33-003 D11).

**Answer all five in writing before implementing.**

## Requirements

and 1 trait, the absent `schema/` directory for `fjell-semantic-format`, and which
of its functions produce bytes — each probe with a control, `/usr/bin/grep -a`.

**R2 — §A–§E answered in writing.**

**R3 — D3/§C:** the hash change, the normalisation rules stated in the tool, and the
inverted test.

**R4 — D4:** the drift, named per item, with the method stated. If a removed field
or method appears, **stop and escalate**.

**R5 — D1/D2/§B:** the goldens captured from the unmodified codec, the rewrite, the
generated file, the Gate 1 comparison, and whatever `Canon` gained.

**R6 — D5's demonstrations**, each with a transcript, each reverted.

**R7 — The counts after:** items in the snapshot, structs and traits now covered by
body, formats with a generated description (it was 17), and what the semantic
codec's file contains.

**R8 — E-067 CLOSED** or survivors named; **E-065 updated** — its first survivor
resolved, the other four still named — with `v1-limitations.md` in the same commit

**R9 — The gates**, each by its own exit status, `test-all`, the repro baseline
re-recorded in the same commit as any rebuild (the codec's crate is linked by
several prebuilts), and a CI run id.

### Non-goals

- Changing the wire format's **design**, its version, or its error precedence.
- Converting E-065's other four survivors.
- The kernel's raw write of `AuditRecordBin` (E-065's own note says that is
  kernel-side and separate).
- Making the snapshot scan more crates than it scans today.

## Risks

**The codec is linked by most services**, so a rewrite that changes one byte changes
prebuilts and the repro baseline. The goldens are the guard, and they must be
captured **before** the first edit — RFC-0.33-003 proved that order works; reversing
it proves nothing.

**A struct-body hash will move on formatting** unless §C is answered deliberately,
and a baseline that moves for reasons nobody can explain is a baseline people
regenerate without looking. That is the exact failure this line exists to remove,
so it would be the worst possible way to close it.
