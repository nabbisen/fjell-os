# RFC-0.41-003 R2–R4 (and the escalation of R1): the encoder zeroes a pair, not the factory

**Governing RFC:** [../accepted/RFC-0.41-003-the-attestation-records-placeholders-stop-reading-as-state.md](../accepted/RFC-0.41-003-the-attestation-records-placeholders-stop-reading-as-state.md)
**Handoff:** [../handoffs/RFC-0.41-003-the-attestation-records-placeholders-stop-reading-as-state/implementation-handoff.md](../handoffs/RFC-0.41-003-the-attestation-records-placeholders-stop-reading-as-state/implementation-handoff.md)

Written against base `21cff44`. **This line is partly done.** R2, R3 and R4 are done; **R1 is not, and neither is
the part of R5 that depends on it**, because R1 moves bytes and the handoff says to stop when a byte moves
(trap 3). E-101 stays ACCEPTED, with a dated progress note.

## Why R1 was not done — the premise of R4 holds for R2 only

R4 says no byte of any record the tree can construct moves. That is true of the **counter pair** (every honest
construction either sets the flag beside its value or writes 0 beside 0). It is not true of R1, in two ways, both
measured on the record `AttestationRecordV2::local` builds today (422 bytes of canonical stream):

* **Writing the placeholders as zero moves 12 bytes of that stream:** the two non-zero keyring epochs (`1`, `1`; the
  third is already `0`), the eight bytes of `snapshot_id` (`"SN000001"`), `rollback.last_advance_source` (`1`) and
  `freshness.key_epoch` (`1`). `snapshot.reason` and `health.status` are already `0`, so for them only the new
  disclosure byte moves anything.
* **Adding an availability disclosure per claim adds bytes** (five, if grouped as the RFC asks: the three keyring
  epochs; the snapshot id with its reason; and `health.status`, `last_advance_source`, `key_epoch` each on their
  own). That changes the stream length (422 → 427) and so every digest the record is signed over.

Either one alone moves the digest of the record `attestd` signs. So R1 is a format change: `SCHEMA_VERSION` 3 → 4,
the golden re-taken, `v2.frozen` regenerated with its field list changed. The handoff says not to bump the
version on my own judgement to make a golden test pass, and this is a persistent signed format. **Escalated.**

What I can say to make the ruling cheap, because the earlier bump left a template: the `golden.rs` sample sets
every claim available, so under the grouped design its v4 stream would be exactly its v3 stream **plus five
flag bytes and the version word** — the same style of proof as `attestation_v3_is_v2_plus_six_flags` applies
(remove the bytes, rewind the version word, recover the v3 golden). The attestation format is not in the ABI
snapshot; what notices a bump is the golden, `v2.frozen`, the registry and the format crate's tests — and
`attestd`'s summary output (R5), which would print the five new disclosures in the same `name=value` shape.

## R2 — the encoder zeroes the counter value

`write_canonical` now writes `rollback.trust_provider_counter_value` as `0` whenever
`rollback.trust_provider_counter_supported` is `0`, and says so with a `note` in the stream description (the
same shape as `digest_zeroed_when_unavailable`). `RollbackClaims` stays `pub` with `pub` fields — changing its
visibility is a stated non-goal — so the hole is closed at the encoder, which holds regardless of visibility.

## R3 — the test that can fail, and was seen failing

`every_flag_and_value_pair_is_zeroed_by_the_encoder_not_by_the_factory` builds the record **by field
assignment**, not through `local()`: it starts from an honest reference (every optional claim unavailable, via
the factory), copies it, and assigns a deliberately non-zero value behind **every** false flag — the five
digests, the measurement section and the counter value — then requires the two canonical streams to be
**byte-identical**. One test covers every pair, as asked. It has a control, because equal streams could also
mean the fields are never encoded at all: with each flag turned on in turn the stream must differ (seven flips,
one per flag).

**Seen red:** against the encoder as it was, it failed on the `assert_eq!` ("a value behind a false flag reached
the encoded bytes"), because the counter value `777` reached the stream. It passes with the encoder change.
(The digests and the measurement section were already encoder-zeroed from RFC-0.40-001; the test confirms that
for the first time by direct construction rather than through `local()`.)

## R4 — the frozen schema and the golden

* `SCHEMA_VERSION` stays **3**.
* `v2.frozen` was regenerated by `cargo xtask schema dump` (never hand-edited): the diff is two added lines — the
  dated header note and the one `note counter_value_zeroed_when_unsupported …` line. **No field line changed.**
  `schema check`: 21 files match their encoders.
* `crates/fjell-schema/src/registry.rs` carries the dated note (shape of the 2026-09-24 precedent: "Corrected
  toward the encoder; no byte moved").
* **The golden digest did not move.** `fjell-schema`'s golden tests (20) and the attestation format's own
  tests (31) pass unchanged; that is the instrument for "no byte moved" for every record the tree can construct.

## R5 — `attestd`'s summary

Nothing new to print for R2: the pair is already printed (`counter_supported=… counter_value=…`). The
disclosures R5 means are R1's, and are waiting on the ruling.

## R6 — limitations row 13, as a report

`v1-limitations.md` row 13 says the record "still carries unqualified placeholders that read as state — its
keyring epochs, snapshot id, health status, `rollback.last_advance_source` and freshness key epoch — which
nothing computes (E-101, ACCEPTED, 0.41)". **It is still exact**: this line changed none of those fields. I
did not edit it. When R1 lands the row will need re-reading, and it will name which claims are then disclosed.
