# RFC-0.40-001 R1–R9: the attestation record stops asserting what never happened

**Governing RFC:** [../accepted/RFC-0.40-001-the-attestation-record-stops-asserting-what-never-happened.md](../accepted/RFC-0.40-001-the-attestation-record-stops-asserting-what-never-happened.md)
**Handoff:** [../handoffs/RFC-0.40-001-the-attestation-record-stops-asserting-what-never-happened/implementation-handoff.md](../handoffs/RFC-0.40-001-the-attestation-record-stops-asserting-what-never-happened/implementation-handoff.md)

Written against base `0555d76`. **E-094 closes in this line** (R8). This line makes the record
*truthful*; it does not make attestation real, and nothing here says it does (R7).

## R1 — re-derived, with controls

| Claim in the RFC | Result |
|---|---|
| `sign_v2` discards `_meas_seq` | held (`#[allow(dead_code)] _meas_seq`) |
| `init` passes the literal `4u64` | **stale.** Since 0.38 it passes `meas_seq`, a value read from `measuredd`. Either way `sign_v2` threw it away, so the record's `head_seq: 1` was the literal inside `dev()`, not anything `init` said. |
| `enter_enforcing()` is unconditional, so `sign_v2` is always the path | held; `sign_v1` is unreachable in practice |
| `attestd` holds only `EP_SLOT = 0` and the readiness send | held (`spawn.rs` installed nothing else for it) |

**The class sweep — a third signed or exported artefact asserting a positive result from a literal:
none.** Command: `/usr/bin/grep -a -rn` over `crates/` for the verified-flag and digest-literal shapes
(`*_verified`, `: true` in record/bundle/report builders, `[0x22; 32]`-style repeats), with the output
of a known-positive control (the `dev()` literals) in the same command. Hits: `#[cfg(test)]` fixtures;
`ReleaseMetadata::dev` (a *dev input*, not an assertion about a verification); `bootctl-model`
(in-memory, never signed or exported); and the live literals in `v2.rs dev()` and `attestd`'s
`sign_v1`. **Boundary:** it finds literals that look like the ones I searched for. It cannot find an
artefact that assembles a positive from non-literal parts. (My first run of this sweep excluded
`*test*` and so also hid every path containing `attestation` and `attestd`; the control was in a
separate command and did not notice. I redid it with the control in the same output.)

## R2 / R3 — field by field

| Field | Before | Now |
|---|---|---|
| `release_verified`, `rootfs_verified`, `policy_verified` | `true` | **`false`** — and `verified_flags()` can set a bit only if the flag is true **and** its digest is available, so no future caller can assert a verification over a missing digest |
| `kernel_digest`, `release_digest`, `rootfs_digest`, `policy_digest`, `snapshot_digest` | literal `0x11…`/`0x22…`… | **zero, with an adjacent availability byte `0`**; the **encoder** zeroes them regardless of what the caller holds |
| measurement section | `head_seq 1`, `chain_digest 0x55…`, range literal | the real head, read from `measuredd`; or, when unreadable, **unavailable** (zero, flag `0`) |

The pattern is `fjell-diag-format`'s, not a second one: a new `ClaimAvailability` of six bytes
(`kernel_digest`, `release_digest`, `rootfs_digest`, `policy_digest`, `snapshot_digest`,
`measurement`) written adjacent to the claims, zeroed by the encoder. **The service-image digest is
not in `kernel_digest`**; I did not put it anywhere.

**Version:** `SCHEMA_VERSION` 2 → 3. `dev()` is gone; `local(…, measurement: Option<…>)` replaces it and
has no way to set a verified flag. What notices the move, since the attestation format is **not** in the
ABI snapshot: the golden test (`attestation` digest `92913e80…8d3e` → `241d4c91…f9b9`), the registry
history note, and `v2.frozen` (regenerated by `schema dump`, only that file changed; `schema check`
reports 21 match). A new test, `attestation_v3_is_v2_plus_six_flags`, removes the six flag bytes from the
v3 sample, rewinds the version word, and recovers the **old** golden digest — so the move is shown to be
exactly "six bytes and a version", nothing else. Cost: any external verifier of v2 records must learn v3;
none exists in the tree.

## R4 — the measurement section is real

`attestd` gets a `CALL` capability to `measuredd` (slot 4, installed in `task/spawn.rs`). The read is
`fjell_service_api::measuredd::read_chain(ep)` — stats, head, stats again; it retries four times and
returns `None` unless both stats agree and cover the head's sequence, so a chain that moved mid-read is
never reported as a coherent head. `diagnosticsd`'s own `query_measurement()` now calls the same function
(the same defect-in-waiting existed in two copies). `sign_v2` no longer takes a sequence, and
`GENERATE` now refuses a non-zero `w0` with `ERR` instead of accepting a number it would ignore; `init`
sends no words.

**Fallback proven, not asserted:** with the capability removed (scratch), the record reports
`measurement=0`, `head_seq=0`, a zero chain digest and `verified_flags=0` — no stale or literal head
appears — and the tier goes red.

## R5 — grant the read, refuse the append

`ImageId::ATTESTD` is out of `source_for_sender`; `attest/tests.rs` moved it from `MAPPED` into
`the_services_that_must_be_refused_are`. Same commit as the capability. **Demonstrated, in the kernel
rather than in the mapping's unit test** (scratch `attestd` code, reverted and proved):

* A) `APPEND_EVENT` and `APPEND_IMAGE_SET` through slot 4 → `ERR 6` both; the chain stays at 4 events.
* B) with the mapping restored (scratch), the same append is accepted and recorded `source=11`, a fifth
  event — so the refusal in A is the mapping, not an accident of the call.

## R6 — the tier

`measurement` now asserts `attestd: record verified_flags=0`, the availability line with
`measurement=1`, `head_seq=4 included=1..4`, and `expect_chain_head` for the printed
`chain_digest sha256:…` — compared against the host's **independent derivation** of the same four events,
as `remote-diag` does, not against non-zero. Pre-change (red): `verified_flags=7`, `head_seq=1`, chain
`0x5555…`. Post-change (green): flags 0, head equal to the host derivation.

## R7 — no retro-claim

`v1-limitations.md` row 13 is rewritten as *says only what is true — and it is not complete*; row 14 says
what is still unmeasured (the kernel's own image) and that release/rootfs/policy verification is E-095.
`measurement-and-attestation.md` ("What an event's source says", "## Attestation") says the same. E-095
gets a dated note: its availability slots and the independent oracle must change when verification becomes
real, so a future line cannot flip a flag without the tier noticing.

## Not done, and where the RFC is wrong

* **Other literals remain in the signed record** and are not in the RFC's table: keyring epochs 1/1/0,
  boot slot 0 / boot id 1, snapshot id `"SN000001"` / reason 0, health target and status,
  `rollback.last_advance_source = UpgradedConfirmation`, `trust_provider_counter_supported = true`,
  `freshness.key_epoch = 1`. I did not touch them: the RFC names the flags and five digests. Whether they
  fall under E-094, or are a successor entry, is the architect's.
* **ABI surface:** the RFC's non-goal is "any addition to the kernel's ABI surface". I added to
  `fjell-service-api` (the shared reader) and the snapshot moved +2. The kernel's own ABI did not move.
  If that reading is wrong, the reader is the thing to revisit.
