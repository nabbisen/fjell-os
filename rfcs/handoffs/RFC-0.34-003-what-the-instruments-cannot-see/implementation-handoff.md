# Developer Handoff — RFC-0.34-003

**Governing RFC:** [RFC-0.34-003](../../accepted/RFC-0.34-003-what-the-instruments-cannot-see.md)
**Milestone:** 0.34
**Status:** inherited from the governing RFC (Accepted, 2026-09-25)
**Audience:** implementation model

This handoff directs execution. It does not redefine the RFC. If you find a
design conflict, **stop and escalate** — do not resolve it in code.

---

## 0. The measure of this line

Two instruments, one question: **what does this check cover, and how would anyone
know?** The measure is not that a file exists or a hash changed. It is that

- a change to the bytes services exchange **cannot be committed** without the
  description changing with it or a gate going red, and
- a field added to a scanned struct, or a method added to the trait, **registers as
  drift**.

## 0.1 You have done this before, and the method is not to be re-derived

RFC-0.33-003 established it and it stands unchanged: **the encoder is the
description**; goldens are captured from the **unmodified** encoder before the first
edit; the file is generated by the same function that writes the bytes; the
comparison runs in Gate 1. RFC-0.33-004 D5 and its §C established the other half:
**a baseline is re-recorded once, and the drift it reveals is read and named**.

Your own enum work is the standard for R4 — the new scanner run over every tag from
`0.10.0`, consecutive lists diffed, and the finding that one variant was removed in
twenty-two releases and it was deliberate. Do the same for structs and the trait.

## 0.2 Settled — do not re-open

1. The codec writes through `Canon`, against goldens captured first (D1).
2. **No second list of fields**; if `Canon` cannot express the shape, `Canon` gains
   what it needs and the gap is **named** (D2).
3. The ABI hash covers a braced struct's fields and a trait's items, same
   normalisation as the enum's, baseline re-recorded **once** (D3).
4. The drift is **read and named**; a removed field or method nobody noticed is
   **escalated, not absorbed** (D4).
5. Five demonstrations, each failing first, including **inverting the test that
   currently asserts the blindness** (D5).
6. E-065's other four survivors are **not touched** (D6).

## 1. Order — §D's lean, and why

**R1 → §A–§E in writing → R3 (the hash, §C's rules, the inverted test) → R4 (the
drift, read) → R5 (goldens, the codec, the generated file, Gate 1) → R6
(demonstrations) → R7 (counts) → R8 (errata) → evidence.**

**E-067 first.** It is the mechanical half, and once it is in place the codec work's
own ABI additions are visible to Gate 4 **by body** rather than by declaration line —
the instrument checks the work that follows it. That is worth more than doing the
interesting half first.

## 2. §C decides whether Gate 4 stays trusted

A struct-body hash that moves on a `rustfmt` reflow will be regenerated without
being read, which is precisely the failure this line removes. So answer, in the
tool's own doc and not only in the answer document:

- comments and whitespace — normalised, as the enum hash does;
- `#[repr(C)]` — **part of the ABI**, in;
- `#[derive(...)]`, other attributes, private fields, field order — each **in or
  out, stated**, with the reason.

Then show a reflow that does **not** move the hash, as a control.

## 3. §B — say what `Canon` cannot say

The nine converted formats were flat field lists. This codec has chunked frames, a
length-prefixed token stream and a sentinel. Extend `Canon` with what it needs, and
where something genuinely cannot be expressed, **the description stops there and the
gap is a named survivor** — the way `fjell-bundle-format`'s big-endian gap is named.
Inventing a second notation for the hard parts is the one outcome worse than a
survivor.

## 4. §A — the decoder is not described, and the file must not imply it is

The frozen file describes the **encoder**. A decoder that reads different fields
than the encoder writes is the class E-045 hid. Provide the round-trip per sample,
**and** state in the file's header or the crate's doc what the description does not
cover on the decode side. Do not let a reader infer that a generated file blesses
the decoder.

## 5. The codec is linked by most services

A one-byte change moves prebuilts and the repro baseline. **Capture the goldens
before the first edit** — that order is what made RFC-0.33-003 safe, and reversing
it proves nothing. Re-record the baseline **in the same commit** as any rebuild, and
run the two-build check before each re-record.

## 6. Prohibited

- A hand-written description of any part of the codec (D2).
- Changing the wire format's design, its version, or its error precedence.
- Converting E-065's other four survivors, or touching the kernel's raw write of
  `AuditRecordBin`.
- Scanning more crates than the snapshot scans today.
- Regenerating the baseline before reading what `--verify` reported.
- Closing E-065 — only its **first survivor** is resolved here; the entry stays with
  four.
- A gate piped into `grep` instead of its own exit status.

## 7. Required evidence

1. R1: the 443 items by kind, the 33 structs and 1 trait, the absent `schema/`
   directory, and which functions of the codec produce bytes — each with a control.
2. §A–§E in writing, §C's rules as they appear in the tool, §B's gap named.
3. R3: the hash change, the inverted test, and the reflow control.
4. R4: the drift per item, by the tag-walk method, with **stop and escalate** if a
   field or method was removed.
5. R5: goldens from the unmodified codec, the rewrite reproducing them, the
   generated file, the Gate 1 run, and whatever `Canon` gained.
6. R6's five demonstrations, each reverted, with transcripts.
7. R7's counts: snapshot items, structs and traits now covered by body, formats with
   a generated description (17 before), and what the codec's file contains.
8. **E-067** resolved or survivors named; **E-065 updated, not closed**; register and
   `v1-limitations.md` in the same commit.
9. The gates, each by **its own exit status**, `test-all`, the repro baseline
   re-recorded in the same commit as any rebuild, and a CI run id.

## 8. Review request

Standard format, in `.git-exclude/review-request/`. Flag for focused review:

- **What the re-record revealed**, first, and anything removed.
- **§C's in/out list**, and the reflow control.
- **§B's gap** — what `Canon` still cannot say about this codec.
- What the description does **not** cover on the decode side.
- Anything outside the *Touches* list, which is indicative.
