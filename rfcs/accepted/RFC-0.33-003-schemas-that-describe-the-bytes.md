# RFC-0.33-003: Schemas that describe the bytes

**Status:** Accepted — by the owner (nabbisen), 2026-09-24; implementation may begin (RFC 000)
**Milestone:** 0.33
**Tracks.** **E-045** — the frozen wire-format schemas were never enforced and
have drifted — and **E-055**, struct padding written to disk through four raw
byte-slice views. They are one line because both change bytes on disk, and doing
that twice is worse than doing it once.
**Touches** *(indicative)*: `crates/formats/*/schema/*.frozen`, the format crates
they describe, `crates/services/fjell-init/src/main.rs`, `fjell-tools`,
`.github/workflows/ci.yml` (`ci-schema-gate`), `docs/src/adr/ADR-v0.6-003`.
**Relates to:** RFC-v0.6-003 (which specified both mechanisms and shipped
neither); E-046 (Finding 4's read side, fixed — this is its write side).

## Summary

### Finding 1 — the files say a tool made them, and the tool does not exist

Eleven `.frozen` files exist. Each is headed **`# generated by fjell-tools schema
dump`**. There is no such subcommand, and no code reads a `.frozen` file:
`ci-schema-gate` checks that eleven named paths exist and are non-empty, which it
says of itself in a comment. So the schema freeze is a set of hand-written files
asserting their own provenance.

### Finding 2 — the drift, measured field by field

`rollback-record-v1.frozen` against `RollbackRecord` today:

| Frozen file | Struct | |
|---|---|---|
| `schema_version u16 LE` | `schema_version: u16` | agrees |
| `channel u8 [16]` | `channel_id: [u8; 8]` | **renamed, and half the width** |
| `min_counter u32 LE` | `min_counter: u64` | **twice the width** |
| `updated_tick u64 LE` | `last_advance_tick: u64` | **renamed** |
| — | `last_advance_source: AdvanceSource` | **absent from the schema** |
| — | `record_digest: Digest32` | **absent from the schema** |

`schema_version` has not moved. A reader who trusted the file would mis-parse
every field after the first, and would not know two exist at all.

### Finding 3 — padding reaches the disk (E-055)

`fjell-init` fills sector buffers by viewing `StoreSuperblock` (twice),
`RecordHeader` and `BootControlBlock` as byte slices —
`from_raw_parts` at four sites. The checksums stopped reading padding in 0.32;
the **bytes written still contain it**, and for struct memory that padding is not
required to be initialised. Nothing reads these back from disk today (E-044),
which is why this is latent rather than live — and why now is the cheap moment.

### Finding 4 — the frozen set is arbitrary

`BootControlBlock` and `StoreSuperblock` — the two structures this project
actually writes to fixed disk locations — **have no `.frozen` file at all**,
while eleven other formats do. So the eleven are not "the wire formats"; they are
the eleven someone wrote files for.

## The settled part

**D1 — A `.frozen` file is generated, or it does not exist.** One generator is
the only thing that writes one, and its output for an unchanged format is
byte-identical to the committed file.

**D2 — A comparison test fails on drift**, in Gate 1, naming the field. The
generator and the check are the same description read two ways, not two
descriptions kept in step by hand — that is the defect this line removes.

**D3 — The drift is resolved toward the code, with the change recorded.** The
struct is what the tree writes and reads; the file is documentation that fell
behind. **Each corrected file carries a dated note of what it used to claim**, so
the record is not silently rewritten.

**D4 — `schema_version` moves where the bytes or the layout moved**, and the
correction says which formats changed and when.

**D5 — E-055's four sites serialise named fields** — the shape RFC-0.32-002 used
for the checksums — so no padding is written. The bytes on disk change, and D4
applies to them.

**D6 — Every format written to disk or sent over IPC has a `.frozen` file, or a
recorded reason why not** (Finding 4). "Nobody wrote one" is not a reason.

**D7 — Demonstrated failing:** a field renamed in a struct turns the comparison
test red and names it; a hand-edited `.frozen` file does too; and the generator's
output for an untouched format is shown byte-identical.

## The open questions

**§A — Where does the generator live, and what is it?** A `fjell-tools schema
dump` subcommand (what the files claim), a build script, or a test that writes
the file and compares? **My lean: the subcommand plus a test that runs it**, so
the file can be regenerated deliberately and drift fails in Gate 1 — but say how
the generator learns a struct's layout without becoming a second description of
it. That question is the whole line: **a generator that hard-codes the fields is
E-045 again with more steps.**

**§B — Is the current `.frozen` DSL the right output?** It is prose-ish (`field
channel u8 [16]`). If the generator emits it, something must parse it back to
compare. **Lean: keep the format, and let the comparison be generated-vs-committed
text** — no parser, no second grammar.

**§C — What about the formats with no file** (Finding 4)? Add them, or declare a
narrower set with a reason? **Lean: add the two disk structures**, since they are
the ones with fixed on-disk locations.

**§D — Do the on-disk bytes change in one commit or two** (E-045's corrections
and E-055's serialisation)? **Lean: E-055 first, then regenerate** — otherwise the
generated file describes a layout that is about to change.

**§E — Does anything read these formats from disk yet?** R1 must say, per format.
If any does, that format's byte change is a migration and this RFC does not cover
migrations.

**Answer all five in writing before implementing.**

## Amended at acceptance, 2026-09-24 — the window §E depends on is still open

Re-derived at the tip this was accepted on, because RFC-0.33-001 landed in
between and this RFC's own Risks section said that line would close the window:

- **Nothing reads any of these formats back from disk.** `storaged`'s
  `READ_CHUNK` arm is still `reply(READ_CHUNK); // placeholder`, and `bootctl`
  builds its block in memory (`BootControlBlock::new`) rather than reading one —
  RFC-0.33-001 deliberately left persistence out (its §A). So **§E's answer is
  still "nothing", and the byte change in D5 is still free.**
- **It stops being free at the first read-back.** `init` writes a
  `BootControlBlock` to both mirrors today; the moment anything parses one, D5
  becomes a migration, which this RFC's Non-goals exclude. **That is the argument
  for doing this line before the persistence line, not after.**
- R1 re-derives both of these rather than trusting this note.

## Requirements

**R1 — Re-derive** Findings 1–4: the eleven files, the absent generator, the
drift per format (not only `rollback-record-v1` — check all eleven), the four
write sites, and whether any format is read back from disk. Use `/usr/bin/grep
-a`, with a control on the file each absence is about (E-055's own cause).

**R2 — §A–§E answered in writing.**

**R3 — D1/D2/§A/§B:** the generator, the comparison, and the Gate 1 run.

**R4 — D3/D4:** each drifted file corrected with its dated note; versions moved
where bytes moved.

**R5 — D5:** the four sites serialising named fields, with a test that the written
sector contains no indeterminate bytes.

**R6 — D6/§C:** every format covered, or its exclusion recorded.

**R7 — D7's three demonstrations**, with transcripts, reverted.

**R8 — `ci-schema-gate` replaced or retired**: a job that checks eleven paths
exist is not the check this line builds, and leaving both is two instruments for
one property.

**R9 — ADR-v0.6-003's schema consequences** corrected to what now holds; **E-045
and E-055 CLOSED** or survivors named, with `v1-limitations.md`.

**R10 — The gates**, each by its own exit status, `test-all`, the repro baseline
re-recorded in the same commit as any rebuild, and a CI run id.

### Non-goals

- Migrating existing on-disk data (§E decides whether that is even possible).
- The store's read side (`READ_CHUNK` is a placeholder — E-044's neighbour).
- New formats, or changing any format's *design*.
- The kernel's four raw reinterpretation sites.

## Risks

**A generator that is a second hand-written description proves nothing** (§A).
If the honest answer is that Rust cannot hand you a layout without a macro or a
build-time reflection step, say so and say what the generator does instead —
including the possibility that the frozen file should describe the *encoder's*
output rather than the struct.

**Changing on-disk bytes nobody reads is safe exactly once.** After E-044's line
wires the boot-control block, it stops being free.
